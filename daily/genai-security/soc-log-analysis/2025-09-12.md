## 🧠 웹 응용프로그램 취약점 정리
### 1. 웹 취약점 개요

#### 개념
웹 응용프로그램은 사용자 입력을 받아 동작하므로 입력 검증 미흡, 인가 부족, 서버 설정 오류 등이 있을 경우 공격자가 악용할 수 있다.
대표적으로 OWASP Top 10이 웹 보안에서 가장 많이 언급되는 취약점 분류 기준이다.

#### 위험성
- 개인정보, 계정정보, 금융정보 탈취
- 시스템 권한 상승 및 서비스 마비
- 웹 서버 장악 및 2차 공격 경유지 활용

### 2. 주요 취약점 유형
#### (1) 디렉토리 인덱싱 / 정보 노출 / 불충분한 인가

- 문제점
    - 디렉토리 인덱싱이 허용되면 `backup.zip`, `config.old` 등 민감 파일 노출
    - 서버 오류 메시지를 통해 DB 구조, 서버 버전 등이 유출
    - 인가 검증 미흡 시, URL 파라미터만 바꿔도 관리자 페이지 접근 가능

- 사례

``` bash
http://example.com/admin?id=1
→ id 값을 바꾸면 다른 사용자 계정 접근 가능
```

#### (2) 파일 다운로드 취약점

- 문제점
    - 다운로드 기능에 경로 검증이 없으면 임의 파일 다운로드 가능
- 예시

``` bash
http://example.com/download?file=../../../../etc/passwd
```
#### (3) 파일 업로드 취약점
- 문제점
    - 업로드 기능에서 확장자/MIME 검증이 없다면 `.php`, `.jsp` 등 웹쉘 업로드 가능

- 공격 예시

``` php
<?php system($_GET['cmd']); ?>
```

- 결과
    - 공격자가 웹서버에서 원격 명령 실행

#### (4) 크로스 사이트 스크립팅 (XSS)

- 유형
    - Stored XSS: 게시판 글에 스크립트 저장 → 다른 사용자가 열람 시 실행
    - Reflected XSS: 검색창 입력값이 바로 응답에 반영될 때 악성 URL로 유도
    - DOM-based XSS: 자바스크립트 동적 처리 시 DOM 객체에 악성 코드 삽입

- 공격 예시

```html
<script>alert('XSS');</script>
http://example.com/search?q=<script>alert('XSS');</script>
```
- 대응
    - 입력 검증: `<`, `>` 같은 특수문자 필터링
    - 출력 인코딩: `&lt;`, `&gt;` 변환
    - CSP(Content-Security-Policy) 적용

#### (5) SQL Injection

- 유형
    - Error-based: 오류 메시지를 통해 DB 구조 유추
    - Union-based: UNION 쿼리로 추가 데이터 조회
    - Blind: 참/거짓 조건을 이용해 데이터 추출

- 공격 예시

``` sql
SELECT * FROM users WHERE id = 1 AND password = '' OR 1=1; -- 
```
- 대응
    - Prepared Statement

``` sql
SELECT username FROM users WHERE username = ?
```

- 입력값 검증 (특수문자 필터링)
    - ORM(Object Relational Mapping) 사용 (예: Spring Data JPA)

### 3. 취약점-대응 정리표

| 취약점           | 공격 예시                       | 대응 방법                    |
| ------------- | --------------------------- | ------------------------ |
| 디렉토리 인덱싱      | `/backup.zip` 노출            | 디렉토리 인덱싱 비활성화            |
| 파일 다운로드       | `../../etc/passwd`          | 경로 검증, 화이트리스트 적용         |
| 파일 업로드        | 웹쉘 업로드                      | 확장자·MIME 검증, 실행권한 제거     |
| XSS           | `<script>alert(1)</script>` | 입력 검증, 출력 인코딩, CSP       |
| SQL Injection | `' OR 1=1 --`               | Prepared Statements, ORM |

## 🧠 웹 방화벽(WAF) 정리
### 1. WAF 개요

#### 개념
WAF(Web Application Firewall)는 웹 애플리케이션에 들어오는 HTTP/HTTPS 요청을 검사하여 공격을 탐지·차단한다.

#### 작동 원리
- 트래픽 모니터링
- 패턴 매칭 (OWASP Top 10 기반)
- 행동 분석 (정상/비정상 행위 구분)
- 요청 차단

### 2. 주요 기능
- 필터링: SQLi, XSS 차단, 허용 트래픽만 전달
- 로깅: 모든 요청/응답 저장 → 공격 추적 가능
- 경고: 의심 행위 시 관리자 알림

### 3. 보호 수준과 한계

#### 보호 가능
- SQL Injection, XSS, CSRF, OWASP Top 10 대응
- 실시간 공격 차단

#### 한계
- 새로운 공격 패턴은 탐지 어려움 → 지속적 규칙 업데이트 필요
- 설정 오류 시 오탐/과탐 발생
- IDS/IPS 등 다른 보안 솔루션과 통합 필요

### 4. ModSecurity (대표 WAF)

#### 특징
- 오픈소스, Apache/Nginx용 모듈
- OWASP CRS(Core Rule Set) 기반
- 실시간 HTTP 요청 검사 및 차단 가능

#### 설정 파일 구조
- `modsecurity.conf`: 메인 설정
- `rules.d/`: 규칙 저장 디렉토리
- `crs-setup.conf`: OWASP CRS 설정

#### 주요 옵션
- `SecRuleEngine`: On/Off/DetectionOnly
- `SecRequestBodyAccess`: 요청 본문 검사 여부
- `SecResponseBodyAccess`: 응답 본문 검사 여부
- `SecAuditLog`: 감사 로그 저장 경로

#### 규칙 예시

``` apache
SecRuleEngine On
SecRequestBodyAccess On
SecResponseBodyAccess On
SecAuditLog /var/log/modsec_audit.log
SecDefaultAction "phase:2,deny,log,status:403"

SecRule ARGS "union select" "id:100002,phase:2,deny,log,status:403,msg:'SQL Injection Detected'"
SecRule ARGS "<script>" "id:100003,phase:2,deny,log,status:403,msg:'XSS Detected'"
```

### 5. 보안 정책과 규칙
- 정책 역할: 예방 – 탐지 – 대응

#### 구성 요소
- 접근 제어 (IP, User-Agent 차단)
- 입력 검증 (SQLi, XSS 차단)
- 오류 처리 (안전한 에러 메시지 제공)

#### 규칙 작성 요소
- 변수: `ARGS`, `REQUEST_URI`, `REQUEST_HEADERS`
- 연산자: `@rx`, `@contains`, `@beginsWith`
- 동작: `deny`, `log`, `status:403`

### 6. 고급 운영
- OWASP CRS(Custom Rule Set): 기본 규칙 세트 제공, 필요에 따라 조정 가능
- 정규표현식(Regex): SQLi, XSS, Base64 인코딩 공격 탐지에 활용
- 로그 분석 + ELK Stack
- Logstash: 로그 수집
- Elasticsearch: 저장/검색
- Kibana: 시각화, 대시보드 제공

| 구분    | 내용                               | 예시             |
| ----- | -------------------------------- | -------------- |
| 기본 기능 | 필터링/로깅/경고                        | SQLi 차단, 로그 기록 |
| 설정 항목 | `SecRuleEngine`, `SecAuditLog` 등 | On/Off, 로그 경로  |
| 규칙 예시 | `SecRule ARGS "<script>" ...`    | XSS 탐지         |
| 한계    | 신종 공격 대응 부족, 오탐 가능               | 규칙 업데이트 필요     |
| 통합    | IDS/IPS, ELK Stack 연동            | 실시간 모니터링       |

## 💻 실습 내용

### 실습 주제: ModSecurity IIS 사용해보기
- 실습 환경
    - 웹 서버: IIS (로컬)
    - 테스트 페이지: default.asp (textarea → msg 파라미터 전달)
    - WAF: ModSecurity (modsecurity.conf 직접 수정)
- 설정
    - modsecurity.conf 맨 아래에 룰 추가
    - 탐지 후 차단(403 Forbidden) 동작하도록 설정

```apache
SecRuleEngine On

# SQL Injection 차단
SecRule ARGS "union select" \
  "id:'100002',phase:1,deny,status:403,nolog"

# XSS 차단
SecRule ARGS "<script>" \
  "id:'100003',phase:1,deny,status:403,nolog"

# Base64 인코딩 페이로드 차단
SecRule ARGS "@rx (?:[A-Za-z0-9+/]{4})*(?:[A-Za-z0-9+/]{2}==|[A-Za-z0-9+/]{3}=)?" \
  "id:'100004',phase:1,deny,status:403,nolog"
```

- 테스트 입력값
    - 정상 입력 → `안녕하세요` ✅ 통과
    - SQL Injection → `1 UNION SELECT username,password FROM users` ❌ 403 Forbidden
    - XSS → `<script>alert(1)</script>` ❌ 403 Forbidden
    - Base64 → `PHNjcmlwdD5hbGVydCgxKTwvc2NyaXB0Pg==` ❌ 403 Forbidden

## ❓ 궁금한 점

- **SQL Injection 대응 방안인 Prepared Statement와 ORM은 어떻게 SQL Injection을 막아주는지. 또한, 개발자가 Prepared Statement를 사용하지 않고도 안전하게 쿼리를 작성할 수 있는 다른 방법이 있을까?**
    - Prepared Statement와 ORM은 사용자 입력값을 **'데이터'**로만 인식하도록 강제하여 SQL Injection을 방어한다. SQL Injection은 사용자 입력값이 **'명령어'**로 해석될 때 발생하는 취약점인데, 이 두 방법은 그 해석 자체를 원천적으로 차단한다.
    - Prepared Statement 원리
        - SQL 쿼리 구조와 데이터 분리: 개발자가 SQL 쿼리문을 먼저 DB에 전달하여 컴파일(준비)시킨다. 이때 쿼리문의 데이터가 들어갈 자리는 '?'와 같은 플레이스홀더로 비워둔다.
        - 데이터만 별도로 바인딩: 이후 사용자 입력값은 플레이스홀더에 '데이터'로만 바인딩되어 전달된다. DB는 이 입력값을 절대 SQL '명령어'로 해석하지 않는다.
        - 예시: SELECT * FROM users WHERE id = ?;라는 쿼리문에 ' OR 1=1이라는 입력이 들어와도, DB는 이를 'OR 1=1'이라는 문자열로만 인식하므로 SQL Injection이 발생하지 않는다.

    - ORM(Object Relational Mapping) 원리
        - ORM은 객체지향 언어의 객체(Object)를 관계형 데이터베이스의 테이블과 매핑해주는 기술이다. ORM은 내부적으로 대부분 Prepared Statement 방식을 사용하므로, 개발자가 직접 SQL 쿼리를 작성하지 않고도 안전하게 DB에 접근할 수 있다. 예를 들어, userRepository.findById(id)와 같은 객체지향 메서드 호출을 통해 자동으로 안전한 SQL 쿼리가 생성된다.

    - Prepared Statement 없이 안전한 쿼리 작성법
        - Prepared Statement와 ORM 외에, **입력값 필터링 및 이스케이프(Escape)**를 통해 SQL Injection을 방어할 수 있다. 사용자 입력값에 ', ", -- 등 SQL 명령어로 해석될 수 있는 특수문자가 포함된 경우, 이 문자들 앞에 이스케이프 문자를 추가하여 DB가 이를 일반 문자로 인식하도록 만드는 방법이다. 하지만 이 방법은 모든 특수문자를 완벽하게 처리하기 어렵고, 누락 시 취약점이 발생할 가능성이 높아 추천되지 않는다.

- **WAF의 성능에 가장 큰 영향을 미치는 요소는 무엇이며, WAF 도입 시 성능과 보안 수준을 적절히 조율하기 위한 기준은 무엇인가?**
    - WAF는 웹 트래픽을 실시간으로 분석하므로 **'패킷 처리량(Throughput)'**과 **'지연시간(Latency)'**에 영향을 준다. 성능에 가장 큰 영향을 미치는 요소는 규칙의 복잡성과 분석 대상의 범위이다.
    - 성능에 영향을 미치는 주요 요소
        - 규칙의 복잡성: WAF의 규칙이 복잡한 정규표현식(Regex)을 많이 포함할수록 CPU 자원을 많이 소모하여 성능이 저하된다. 특히 **비효율적인 정규표현식(.* 등)**은 시스템 전체에 큰 부하를 줄 수 있다.
        - 분석 대상의 범위: HTTP 요청 헤더, 바디, 응답 바디 등 WAF가 검사해야 하는 범위가 넓을수록, 그리고 암호화된 HTTPS 트래픽을 복호화하여 검사할수록 성능 부하가 커진다.
        - 트래픽 양: 초당 처리해야 하는 웹 트래픽 양이 많을수록 WAF의 처리 능력(Throughput) 한계에 도달할 위험이 높다.

    - 성능과 보안 수준 조율 기준
        - 위험도 기반 규칙 적용: 모든 규칙을 무조건 '차단(deny)'으로 설정하기보다, 위험도가 높은 취약점(예: SQL Injection, 파일 업로드) 관련 규칙은 엄격하게 적용하고, 위험도가 낮은 정보성 규칙(예: 스캐닝 시도)은 '탐지(log)' 위주로 운영하여 오탐을 줄이고 성능 부하를 완화한다.
        - 분석 대상 최소화: 불필요한 트래픽(예: 이미지, CSS 파일 등)은 WAF 검사에서 제외하고, 입력값이 포함된 요청(POST, GET)만 검사하도록 범위를 최소화한다.
        - 최적화된 규칙 사용: 복잡한 정규표현식을 피하고, 자주 사용되는 규칙은 캐싱(Caching)을 활용하여 성능을 개선한다.

- **SPA나 RESTful API를 사용하는 서비스에서도 WAF가 효과적으로 동작할 수 있나요? WAF가 API 기반의 공격(예: 불충분한 인가)을 탐지하고 방어하는 방식에 대해 알고 싶습니다.**
    - WAF는 전통적인 웹 환경뿐만 아니라 SPA나 RESTful API 환경에서도 효과적으로 동작할 수 있다. WAF는 HTTP/HTTPS 프로토콜 기반의 요청을 검사하므로, API 호출 역시 동일한 방식으로 분석이 가능하다.
    - SPA/RESTful API 환경에서의 WAF 역할
        - SQL Injection, XSS 방어: API 요청의 파라미터나 JSON/XML 바디에 SQL Injection이나 XSS 페이로드가 포함된 경우, WAF는 이를 탐지하여 차단할 수 있다.

        - 민감 정보 노출 방어: API 응답에 개인정보나 민감한 시스템 정보가 포함되어 있을 경우, WAF가 이를 탐지하여 차단하거나 마스킹(Masking) 처리할 수 있다.

        - API Rate Limiting: 특정 IP에서 비정상적으로 많은 API 호출이 발생하는 경우, WAF는 이를 탐지하여 해당 IP를 차단함으로써 DoS/DDoS 공격을 방어한다.

    - API 기반 공격 탐지 및 방어 방식
        - 불충분한 인가(Broken Access Control) 방어: WAF는 요청 헤더의 **토큰(JWT 등)**이나 쿠키를 분석하는 규칙을 적용하여 특정 사용자만 접근할 수 있는 API에 외부 요청이 들어올 경우 차단할 수 있다. 하지만 이는 사용자별 권한을 세밀하게 관리하는 애플리케이션의 내부 로직을 완전히 대체할 수는 없다.

        - 입력값 검증: API의 요청 바디(JSON, XML)에 대한 스키마(Schema) 유효성 검사를 통해, API가 예상하는 데이터 구조와 다른 비정상적인 요청을 탐지하여 차단할 수 있다.

        - 자동화된 공격 탐지: 봇(Bot)을 이용한 API 공격(예: 계정 생성, 스크래핑)이 증가함에 따라, WAF는 AI/머신러닝 기반의 행동 분석을 통해 사람의 행위와 봇의 행위를 구분하여 차단하는 기능을 제공하기도 한다.
