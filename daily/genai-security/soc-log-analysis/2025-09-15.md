## 🧠 주요 개념 정리

### Ⅰ. Splunk 이해
#### 1. Splunk 개요

- **Splunk 정의**
    - Splunk는 **머신 데이터(Machine Data)**를 다루는 실시간 플랫폼이다.
    - 머신 데이터란 서버, 네트워크, 보안 장비, IoT 기기, 애플리케이션 등 IT 시스템이 동작하면서 자동으로 생성하는 모든 로그와 이벤트 데이터를 의미한다.
    - 기존에는 이 데이터를 단순 저장하거나 사람이 직접 확인했지만, Splunk는 이를 수집 → 저장 → 분석 → 시각화까지 한 번에 처리한다.

- **머신 데이터의 예시**
    - **서버/네트워크 로그** : 서버 에러 로그, 방화벽 로그
    - **응용 프로그램 로그** : 웹 서비스 접속 기록, DB 에러 로그
    - **IoT 장치 데이터** : 센서 값, 기기 동작 상태
    - **기타** : 텍스트 기반 로그라면 모두 가능

> ➡️ 즉, Splunk는 “IT 인프라와 애플리케이션이 남기는 흔적을 한눈에 볼 수 있게 하는 플랫폼”이다.

#### 2. Splunk의 **특징**
- **No Limits**
    - 데이터 형식·용량·속도에 제약이 없다.
    → CSV, JSON, 로그 파일, 대용량 스트리밍 데이터 모두 처리 가능.

- **End-to-End**
    - 외부 데이터베이스나 별도 에이전트 없이도 수집부터 시각화까지 한 번에 할 수 있다.

- **Real-time**
    - 데이터가 들어오는 즉시 인덱싱하고 분석할 수 있다.
    → 보안 이벤트 탐지나 실시간 모니터링에 적합하다.

- **Platform**
    - 앱과 플러그인을 통해 쉽게 기능 확장 가능.
    - Splunkbase에 1500개 이상의 앱이 공개되어 있어 보안, IT운영, 비즈니스 등 목적에 따라 추가 활용이 가능하다.

#### 3. Splunk 플랫폼 활용 영역

- **IT 운영**
    - 클라우드 인프라, 애플리케이션 성능 모니터링
    - 장애 발생 시 원인 추적
- **보안(Security)**
    - 이상 징후 탐지 (내부자 위협, 침입 공격)
    - 침해사고 포렌식, SOC 자동화
- **IoT**
    - 센서 데이터 실시간 모니터링
    - 산업제어시스템(ICS) 보안
    - 예측 분석 (장애/고장 미리 예측)
- **비즈니스**
    - 고객 행동 분석, 경험 최적화
    - 디지털 마케팅 성과 측정
- **개발자**
    - 로그 기반 성능 분석, CI/CD 파이프라인 모니터링

> ➡️ 단순 “로그 수집기”가 아니라, IT 운영 + 보안 + 비즈니스 의사결정까지 아우르는 범용 데이터 분석 플랫폼임을 알 수 있습니다.

#### #### 4. Splunk Apps

- **Splunk 앱 = 대시보드 + 패널 + UI 요소의 묶음**
- 저장된 검색(Saved Searches)을 기반으로 실행되며, 특정 목적에 맞게 패키징 되어 제공된다.
- 커스터마이징 가능 → 직접 만든 앱을 Splunkbase에 배포할 수도 있다.
- 예: 보안 로그 분석용 앱, 클라우드 모니터링 앱

### Ⅱ. Splunk 구성과 메타데이터
#### 1. Splunk 기본 구성

Splunk는 크게 Forwarder → Indexer → Search Head 구조로 동작한다.

- **Forwarder**
    - 원격 서버에 설치되어 데이터를 수집 후 Indexer로 전송.
    - Universal Forwarder: 가볍고 단순, 원시 데이터 그대로 전송
    - Heavy Forwarder: 필터링/처리 후 전송 가능

- **Indexer**
    - 데이터를 인덱싱(색인화) 하여 빠르게 검색할 수 있도록 저장.
    - 통계 처리와 정렬(stats, sort, dedup) 기능 제공.

- **Search Head**
    - 사용자가 작성한 검색 쿼리(SPL)를 Indexer에 전달하고,
    - 여러 Indexer에서 받은 결과를 통합해 시각화/대시보드로 보여줌.

- **Deployment Server**
    - 여러 인스턴스와 클러스터를 관리하고, 라이선스도 중앙에서 제어.

> ➡️ 이 구조 덕분에 Splunk는 분산 확장성과 실시간 처리 능력을 동시에 확보 가능

#### 2. 인덱스 저장 구조 (버킷 구조)

데이터는 **시간 흐름에 따라 버킷(bucket)**에 저장된다.

- **Hot**: 새로 들어온 데이터, 쓰기 가능
- **Warm**: Hot에서 롤링된 데이터
- **Cold**: 오래된 데이터
- **Frozen**: 더 이상 사용하지 않는 데이터
- **Thawed**: 필요 시 복구한 데이터

> ➡️ 이렇게 단계별로 관리하여 성능과 저장공간을 균형 있게 유지한다.

#### 3. 메타데이터 필드

Splunk는 데이터를 단순 저장하지 않고, 메타데이터 필드를 자동으로 붙인다.

- **기본 필드**
    - `_raw`: 원본 로그
    - `_time`: 이벤트 발생 시각
    - `_index`: 저장된 인덱스명
    - `host`: 발생한 서버/장비명
    - `source`: 발생한 파일·스트림 경로
    - `sourcetype`: 데이터 형식(예: access_log, syslog)
    - `linecount`: 이벤트 라인 수

- **시간 필드**
    - date_year, date_month, date_hour, date_wday, date_zone 등
    - 타임스탬프를 세분화해 검색/집계 가능

> ➡️ 예: host=web01 sourcetype=access_log status=404 와 같이 조건 검색이 가능.

#### 4. 인덱스 종류

- **기본 인덱스**
    - `main`: 일반 이벤트 데이터 저장
- **내부 인덱스**
    - `_internal`: Splunk 자체 로그
    - `_metrics`: 성능/메트릭 데이터
    - `_audit`: 사용자 검색 이력, 감사 기록
    - `_introspection`: Splunk 환경 자체 모니터링 데이터

> ➡️ 관리자는 내부 인덱스를 통해 Splunk 자체 상태도 모니터링할 수 있다.

### Ⅵ. Splunk 검색 앱
#### 1. 앱 구성 요소
- Search & Reporting 앱: Splunk 기본 검색 앱
- 주요 UI 요소
    - **검색창(Search Bar)**: SPL(Search Processing Language) 입력
    - **시간 범위 선택기(Time Range Picker)**: 분석 구간 지정
    - **검색 결과 탭**: 이벤트 리스트, 통계, 시각화 확인
    - **타임라인(Timeline)**: 이벤트 분포를 시간축으로 표현
    - **이벤트 뷰어(Event Viewer)**: 개별 이벤트 상세 분석

> ➡️ 이 앱을 통해 로그에서 **“어떤 이벤트가 언제, 몇 건 발생했는가”**를 직관적으로 확인할 수 있다.

#### 2. 시간 범위 설정
- **상대적 시간**
    - `earliest=-30m@h latest=now` → 현재 시점부터 30분 전까지
    - `earliest=-2d@d latest=@d` → 이틀 전 자정부터 오늘 자정까지
- **절대 시간**
    - `earliest=2025-09-15:12:30:00` → 특정 시점부터 검색
- **시간 단위 약어**
    - `s`(초), `m`(분), `h`(시간), `d`(일), `w`(주), `mon`(월), `q`(분기), `y`(년)

> ➡️ 보안 분석에서는 “지난 1시간 동안의 접속 실패”,
운영 분석에서는 “지난 30일간의 트래픽 추이” 등을 빠르게 필터링할 수 있다.

#### 3. 검색 Job 관리
- 모든 검색은 Job 단위로 실행 → Job이 끝난 후에도 일정 시간 결과 유지
- 기본 유지 시간: 10분
- 기능
    - 결과 공유/저장
    - 보고서 예약 (정기 실행)
    - 링크 생성 (최대 7일 연장 가능)

> ➡️ 여러 명이 같은 데이터를 반복 조회할 필요 없이, 공유된 Job 결과를 보면서 협업할 수 있다.

#### 4. 필드(FIELD) 관리
- Splunk는 이벤트 로그에서 자동으로 필드 추출
- 두 가지 영역
    - **Selected Fields**: 자주 쓰는 주요 필드 (예: clientip, action, status)
    - **All Fields**: 전체 필드
- 관리자가 중요 필드를 Selected에 등록해두면, 분석 속도와 편의성이 크게 올라간다.

> ➡️ 예: 웹 보안 분석 시 clientip + status만으로도 공격 패턴(다수의 404, 403 요청)을 빠르게 잡아낼 수 있다.

#### 5. SPL(Search Processing Language)
**5-1. SPL 개요**
- Splunk의 검색 언어 → 검색어 + 파이프(|) 기반 명령어 체인
- 기반 철학
    - Unix 파이프라인 + SQL
    - 시계열(time-series) 데이터 최적화
- **특징**
    - 160개 이상 명령어 지원
    - 검색/필터링/변경/시각화 가능
    - 머신러닝 기능도 일부 포함 (예: 이상 탐지)

**5-2. 검색 예제**

``` sql
index=security sourcetype=linux_secure fail* 
| top user 
| fields – percent
```

- 보안 로그에서 fail이 포함된 이벤트 검색
- 상위 사용자별 이벤트 집계 → percent 필드 제거

> ➡️ 보안 운영에서 “누가 로그인 실패를 가장 많이 했는가?”를 바로 확인할 수 있음.

**5-3. 명령어 체인 예시**

``` sql
sourcetype=access_* status!=200
| eval KB=bytes/1024
| stats sum(KB) dc(clientip)
| rename sum(KB) AS "Total KB" dc(clientip) AS "Unique Customers"
```

- `status!=200` → 웹 접속 실패 로그 검색
- `eval` → 바이트 단위를 KB로 변환
- `stats` → 총 전송량과 고유 고객 수 집계
- `rename` → 읽기 쉽게 컬럼명 변경

> ➡️ 단순 로그를 고객 행동 통계로 변환하는 과정.

**5-4. 주요 SPL 명령어**
- **검색/필터링**
    - `search`, `where`
- **통계**
    - `stats`, `top`, `rare`, `count`
- **변환**
    - `eval`, `rename`, `fields`
- **정렬/중복 제거**
    - `sort`, `dedup`
- **시각화**
    - `chart`, `timechart`

> ➡️ SQL을 아는 사람이라면 stats = GROUP BY, eval = 계산식 추가 정도로 이해하면 쉽다.

**5-5. 연산자**
- **논리 연산자**: `AND`, `OR`, `NOT` (대문자 필수)
- **비교 연산자**: `=`, `!=`, `<`, `>,` `<=`, `>=`
- **와일드카드**: `*` (문자열 패턴 매칭)
- **예제**

```sql
sourcetype=access_* status!=200 action=purchase
```

> ➡️ 구매 시도가 있었으나 성공하지 못한 이벤트만 필터링.

#### 6. 웹로그 분석 실습 예시

- **성공한 구매**

``` sql
index=main sourcetype=access_* status=200 action=purchase
```

→ 정상 응답(200)과 구매 이벤트만 추출

- **실패한 구매**

``` sql
index=main sourcetype=access_* NOT status=200 action=purchase
```

→ 구매 이벤트 중 실패(비정상 응답 코드 포함)

- **차이점**
    - `status=200`: 성공
    - `status!=200`: 실패 (단, NULL 제외)
    - `NOT status=200`: 실패 + NULL 포함

> ➡️ 실무에서는 NOT status=200이 더 안전한 검색식이다. (로그에 누락된 상태 코드까지 감지 가능)

| **정의** | 머신 데이터를 수집·저장·분석·시각화하는 **실시간 플랫폼** |
| **머신 데이터 예시** | 서버/네트워크 로그, 애플리케이션 로그, IoT 기기 로그, 텍스트 데이터 |
| **특징** | - **No Limits**: 형식·용량·속도 제약 없음 <br> - **End-to-End**: 수집부터 시각화까지 일원화 <br> - **Real-time**: 실시간 분석, 분산 확장 <br> - **Platform**: 앱·플러그인 확장 가능 (Splunkbase) |
| **활용 영역** | - **IT**: 클라우드/앱/인프라 모니터링 <br> - **보안**: 위협 탐지, SOC 자동화, 포렌식 <br> - **IoT**: 센서 모니터링, 예측 분석 <br> - **비즈니스**: 고객 행동·프로세스 분석 <br> - **개발자**: 로그 기반 성능 분석   |

#### 2. Splunk 구성 요소

| 구성요소               | 역할                                                                                                          |
| --------------------- | ------------------------------------------------------------------------------------------------------------ |
| **Forwarder**         | 원격에서 로그 수집 후 Indexer로 전송 <br> - Universal: 가볍고 단순, 원시 데이터 전송 <br> - Heavy: 필터링 후 전송 가능 |
| **Indexer**           | 데이터 인덱싱 및 저장 <br> 빠른 검색/통계 처리 (stats, sort, dedup 등)                                             |
| **Search Head**       | 사용자 검색 요청 전달 → Indexer 결과 통합 → 분석·시각화                                                            |
| **Deployment Server** | 인스턴스/클러스터/라이선스 관리                                                                                   |

➡️ 기본 구조: Forwarder → Indexer → Search Head

#### 7. SPL (Search Processing Language)
**주요 명령어**

| 종류      | 명령어                             | 설명         |
| ------- | ------------------------------- | ---------- |
| 검색/필터링  | `search`, `where`               | 조건 검색      |
| 통계      | `stats`, `top`, `rare`, `count` | 집계/빈도 분석   |
| 변환      | `eval`, `rename`, `fields`      | 계산, 컬럼명 변경 |
| 정렬/중복제거 | `sort`, `dedup`                 | 데이터 정리     |
| 시각화     | `chart`, `timechart`            | 그래프/차트 생성  |

- **연산자**
    - 논리: AND, OR, NOT (대문자 필수)
    - 비교: =, !=, <, >, <=, >=
    - 와일드카드: * (문자열 패턴 매칭)

- **검색 예시**

``` sql
index=security sourcetype=linux_secure fail* 
| top user 
| fields – percent
```

➡️ 보안 로그에서 실패 이벤트 추출 → 상위 사용자별 집계

```sql
sourcetype=access_* status!=200
| eval KB=bytes/1024
| stats sum(KB) dc(clientip)
| rename sum(KB) AS "Total KB" dc(clientip) AS "Unique Customers"
```

➡️ 실패한 웹 접근 로그에서 전송량과 고유 고객 수 집계

#### 8. 웹로그 분석 예시

| 목적         | SPL 예시                                                          |
| ---------- | --------------------------------------------------------------- |
| **성공한 구매** | `index=main sourcetype=access_* status=200 action=purchase`     |
| **실패한 구매** | `index=main sourcetype=access_* NOT status=200 action=purchase` |

➡️ status=200: 성공 / status!=200: 실패 (NULL 제외) / NOT status=200: 실패+NULL 포함

#### 📊 전체 흐름 요약

- **데이터 수집**: Forwarder에서 로그 수집
- **저장/인덱싱**: Indexer에서 인덱싱 → 버킷 구조로 관리
- **검색/분석**: Search Head에서 SPL 실행
- **시각화**: 차트, 대시보드, 리포트 생성
- **활용**: 보안(위협 탐지), IT(모니터링), 비즈니스(고객 분석)

## ❓ 궁금한 점

- **기존 SQL 기반 데이터베이스와 비교했을 때, SPL은 어떻게 복잡하고 비정형적인 로그 데이터를 더 쉽게 분석할 수 있도록 돕나?**
    - 기존 SQL은 정형화된 테이블과 스키마에 데이터를 저장하고 분석하는 데 최적화되어 있다. 반면, SPL은 비정형 로그 데이터의 특성에 맞춰 설계되었기 때문에, 로그 분석에 있어 SQL보다 훨씬 유연하고 강력한 이점을 가진다.
    - **스키마 없는 데이터 분석**: SPL은 데이터를 인덱싱할 때 미리 정해진 스키마를 요구하지 않는다. 로그가 Splunk에 수집되면, SPL은 검색 시점에 데이터를 파싱하여 key=value 형태로 필드를 자동으로 추출한다. 이는 로그 형식이 불규칙하거나 수시로 변경되더라도, 즉각적인 검색과 분석이 가능하게 만듭니다. 반면 SQL은 데이터를 저장하기 전 필드와 데이터 타입을 미리 정의해야 하므로, 스키마가 없는 로그 데이터를 다루기 어렵다.
    - **파이프(|)를 활용한 순차적 처리**: SPL은 유닉스 셸의 파이프(|) 개념을 도입하여 여러 명령어를 연결해 복잡한 분석을 단순화한다. 예를 들어, index=web_logs | stats count by clientip | sort -count 와 같이, 검색, 통계, 정렬 단계를 파이프 하나로 연결할 수 있다. 이는 복잡한 중첩 쿼리나 조인(JOIN)을 사용해야 하는 SQL보다 직관적이고 가독성이 높다.
    - **시계열 데이터 처리의 용이성**: SPL은 시간 기반으로 데이터를 처리하는 데 최적화되어 있다. timechart나 streamstats와 같은 명령어를 통해 시간대별 트렌드나 특정 이벤트의 발생 빈도를 쉽게 시각화하고 분석할 수 있습니다. 이는 보안 위협의 패턴을 파악하거나 시스템의 성능 변화를 추적하는 데 매우 유용하다.

- **스플렁크의 버킷 구조(Hot, Warm, Cold 등)가 페타바이트(PB) 규모의 로그 데이터를 저장해야 하는 기업에게 어떤 주요 운영 및 비용적 이점을 제공하나?**
    - 스플렁크의 버킷 구조는 데이터의 접근 빈도와 저장 비용을 고려한 계층적 관리 시스템이다. 이는 대량의 로그 데이터를 효율적으로 저장하고 관리하는 데 핵심적인 역할을 한다.
    - **운영 효율성**: 버킷 구조는 검색 성능을 극대화한다. 자주 검색되는 최근 데이터는 Hot 버킷에 저장되어 SSD와 같은 고속 스토리지에 유지되므로 빠른 검색이 가능하다. 반면, 과거 데이터는 Cold 버킷으로 옮겨져 HDD와 같은 저렴하고 대용량의 스토리지에 저장된다. 이를 통해 시스템은 사용 빈도가 높은 데이터에 리소스를 집중하고, 오래된 데이터는 효율적으로 관리한다.
    - **비용 절감**: 로그 데이터는 시간이 지날수록 검색 빈도가 현저히 줄어든다. 버킷 구조를 통해 기업은 오래된 데이터를 저렴한 스토리지로 이동시킬 수 있다. 예를 들어, 최근 한 달간의 데이터는 고성능 스토리지에 두고, 그 이전 데이터는 저렴한 HDD 또는 클라우드 스토리지(Amazon S3, Azure Blob)로 옮겨 저장 비용을 크게 절감할 수 있다.
    - **'모든 데이터를 Hot 버킷에 저장하는 것이 불가능한 이유'**: 모든 데이터를 고성능 스토리지에 저장할 경우, 스토리지 용량 부족 문제에 직면하게 되고 이는 막대한 비용을 초래한다. 또한, 수많은 데이터 파일이 뒤섞여 있어 검색 인덱스가 비대해지면서 검색 성능이 오히려 저하될 수 있다.

- **스플렁크의 "End-to-end" 개념이 보안관제센터(SOC) 분석가의 업무를 어떻게 간소화하나?**
    - Splunk의 'End-to-end' 개념은 데이터 수집, 저장, 분석, 시각화까지의 전 과정을 하나의 플랫폼에서 제공하는 것을 의미한다. 이는 SOC 분석가가 여러 도구를 오가며 발생하는 비효율성을 제거하고, 위협 탐지 및 대응 시간을 획기적으로 단축시킨다.
    - **단일 플랫폼에서 작업**: 기존에는 로그 수집을 위해 Filebeat, Logstash와 같은 별도의 도구를 사용하고, 저장소로 Elasticsearch나 Hadoop을 사용하며, 시각화를 위해 Kibana와 같은 또 다른 도구를 연동해야 했다. 이 과정은 각 도구의 호환성 문제, 데이터 포맷 변환, 관리 부담 등으로 인해 매우 복잡해진다. Splunk는 이 모든 과정을 하나의 플랫폼에서 처리하므로, 분석가는 도구 간의 스위칭 없이 오직 분석에만 집중할 수 있다.
    - **실시간 가시성 확보**: Splunk는 데이터가 들어오는 즉시 인덱싱하여 실시간으로 검색 가능하게 만든다. 이는 공격 발생 직후의 비정상 행위를 즉시 탐지하고, 공격자의 활동을 추적하는 데 필수적이다. 여러 도구를 사용할 경우, 데이터가 최종 분석 환경에 도달하기까지 지연 시간이 발생하여 초기 대응 시간을 놓칠 수 있다.
    - **간소화된 사고 대응**: SOC 분석가는 Splunk의 SOAR(Security Orchestration, Automation and Response) 앱과 같은 기능을 활용하여 특정 경보 발생 시 자동으로 관련 로그를 수집하고, 위협 인텔리전스와 연계하며, 침해된 시스템을 격리하는 등의 대응 절차를 자동화할 수 있다. 이는 수동으로 처리하던 반복적인 업무를 줄여 분석가가 더 복잡하고 중요한 위협에 집중할 수 있도록 돕는다.
