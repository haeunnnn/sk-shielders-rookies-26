## 🧠 주요 개념 정리

### 오전 워밍업: 취약점 진단과 AI와의 관계
취약점 진단은 시스템의 보안 구멍을 찾아내는 행위이며, 이 과정에 AI가 접목되면서 두 가지 방향으로 발전하고 있다.
- **AI for Security** : AI를 활용해서 취약점을 진단하는 분야
    - **개념** : AI 모델이 방대한 양의 보안 데이터(취약점 보고서, 공격 패턴, 코드 등)를 학습하여, 인간이 놓칠 수 있는 새로운 취약점을 발견하거나, 기존의 취약점 진단 과정을 자동화하고 효율성을 높이는 데 사용된다.
    - **강점** : 반복적이고 정형화된 취약점 진단(체크리스트 기반)을 자동화하여 속도와 정확성을 높일 수 있다. 또한, 기존에 알려지지 않은 이상 징후를 탐지하는 데 유용하다.
    - **필요 역량** : AI 모델을 개발하고, 보안 데이터를 수집, 정제, 학습시키는 **기획, 아이디어, 창의성**이 필요하다. 단순히 코드를 짜는 것을 넘어, '어떤 데이터를 학습시켜 어떤 취약점을 찾아낼 것인가'에 대한 깊은 고민이 중요하다.
- **Security for AI** : AI 자체를 대상으로 취약점을 진단하는 분야
    - **개념** : AI 모델 또한 하나의 소프트웨어이므로, 기존 소프트웨어처럼 취약점을 가질 수 있다. 예를 들어, 학습 데이터 조작, 모델 무결성 훼손, 추론 과정의 조작 등 다양한 공격에 노출될 수 있다. Security for AI는 이러한 **AI 모델의 보안 취약점을 찾아내고 방어하는 것**을 목표로 한다.
    - **강점** : AI 시스템의 신뢰성과 안전성을 확보하여 AI가 오용되거나 악의적으로 조작되는 것을 방지한다. (예: 자율주행차가 특정 패턴에 오작동하도록 유도하는 공격 등)
    - **필요 역량** : AI 모델의 동작 원리에 대한 깊은 이해와 함께, AI 시스템에 특화된 새로운 유형의 취약점을 발굴하고 대응하는 능력이 요구된다.

### 1. HTTP

#### 트랜잭션
- **트랜잭션(Transaction)** : 요청(Request)과 응답(Response)으로 이루어지는 하나의 거래 단위이다. 웹 브라우저에서 페이지를 요청하고, 서버에서 해당 페이지를 보내주는 과정 전체가 하나의 트랜잭션이라고 볼 수 있다.
- **세션(Session)** : 사용자가 웹사이트에 접속하여 로그아웃할 때까지의 상태를 유지하는 논리적인 연결 단위이다. 즉, **활성화된 트랜잭션의 집합**이라고 볼 수 있다.
    - **보안 설계** : 로그인된 사용자의 세션은 중요 정보를 다루기 때문에, **세션 단위의 보안 설계**가 필수이다. 예를 들어, **세션 단위로 인증을 관리하고, 비활성화된 세션은 자동으로 로그아웃**시키는 정책을 적용한다. 30분 자동 로그아웃 정책은 30분 동안 트랜잭션이 없으면 세션을 비활성화한다는 뜻이다.
    - **로그 분석** : **모든 트랜잭션 로그를 분석**하여 세션 단위로 사용자의 행동을 파악하고, 비정상적인 행위(예: 짧은 시간 내에 비정상적인 트랜잭션 발생)를 탐지하는 데 활용된다.
- **분산 병렬 컴퓨팅** : 대규모 트랜잭션(동시 접속 100만 개/초)을 실시간으로 분석하기 위해서는 단일 서버로는 한계가 있다. 이때 **분산 병렬 컴퓨팅(클라우드)** 기술을 활용한다. 전 세계의 수많은 서버 자원을 하나로 묶어 가상의 볼륨에서 데이터를 처리함으로써, **실시간 분석 및 확장성**을 확보할 수 있다.
- **미러링(Mirroring) vs. 태핑(Tapping)** : 네트워크 장비는 제한적인 CPU와 메모리로 인해 모든 패킷을 실시간으로 분석하기 어렵다. 따라서 다음과 같은 방식으로 패킷을 복제하여 별도 분석 장비로 보낸다.
    - **미러링** : 네트워크 스위치의 특정 포트로 들어오는 패킷을 다른 포트로 **복제(Mirror)**하여 보낸다. 보통 패킷의 헤더 정보만 남기고 바디의 **콘텐츠만 추출하여 가공, 전처리**한 후 저장한다. **디지털 미러링**이라고 부르기도 한다.
    - **태핑(Tapping)** : 네트워크 통신 선로에 **별도의 장비(TAP)**를 연결하여 통과하는 **모든 패킷(헤더와 바디 전체)**을 그대로 **덤프(Dump) 떠서 저장**하는 방식이다. 미러링보다 더 상세한 정보를 얻을 수 있어 **디지털 포렌식**의 핵심 증거 수집 방법으로 사용되며, 증거의 무결성을 유지하는 **'Chain of Custody(보관 증명 절차)'**가 중요하다.

#### 서버리스: 애플리케이션 보안의 새로운 패러다임
서버리스(Serverless)는 서버를 직접 관리하지 않고, 필요할 때만 코드를 실행하고 실행된 만큼만 비용을 지불하는 클라우드 컴퓨팅 모델이다.

- **서버리스 동작 원리** : 사용자가 API를 호출하면, 클라우드 제공업체가 **'서버(함수)'를 생성**해서 코드를 실행하고, 실행이 끝나면 **'서버'를 삭제**한다. 이 과정이 0.001초 내외로 매우 빠르게 이루어지는 것이다.
- **개발 환경의 변화** : 서버리스는 프론트엔드 개발자가 서버리스 기능을 이용해 백엔드 로직까지 직접 구현할 수 있게 해주면서 **풀스택 개발자**의 역할을 넓히고 있다. 클라우드에 대한 이해가 높을수록 애플리케이션 보안을 더 쉽게 할 수 있는 환경이 조성된다. 이는 **개발과 보안이 통합된 'DevSecOps'**의 가치를 더욱 강조한다.
- **서버리스 특징**
    - **콜드 스타트(Cold Start)** : 오랜 시간 동안 호출되지 않은 함수는 처음 호출될 때 초기화 과정이 필요하여 약간의 지연이 발생한다.
    - **메모리 사이즈** : 함수 실행에 할당되는 메모리 크기가 상대적으로 작다.
    - **무상태(Stateless)** : 서버리스 함수는 호출이 종료되면 삭제되기 때문에, 함수 내부에 어떤 상태(사용자 정보, 세션 등)도 저장하지 않는다.
- **Q. 애플리케이션 보안을 위해 서버리스의 어떤 부분을 이해해야 할까?**
    - **Stateful(상태) vs. Stateless(무상태)**
        - **Stateful** : 쿠키/세션과 같이 **서버에 사용자 상태 정보를 저장**하는 방식이다. 부하 분산 시 라우팅이 변경되면 기존 세션 정보가 유실될 위험이 있어, 특정 서버에만 접속하도록 세션 고정(Session Affinity) 설정이 필요하다. 주로 TCP 통신에 사용된다.
        - **Stateless** : **상태 정보를 클라이언트가 가지고 있거나, 서버에 저장하지 않는 방식**이다. 서버는 매 요청을 독립적인 것으로 간주한다. 이 때문에 부하 분산에 유연하고 확장성이 뛰어나다. 주로 UDP나 HTTP 통신에 사용된다. **서버리스는 Stateless의 대표적인 예**이며, 이 특성 때문에 보안 설계 시 **상태 정보를 클라이언트(토큰 등)가 안전하게 관리하도록** 해야 한다.
    - **API 보안** : 서버리스는 API 호출을 통해 동작하므로, **API 보안**이 매우 중요하다.
        - **REST API vs. WEB API** : **REST API**는 URI 형태로 자원(Resource)을 명확하게 표현하는 규격이다. **WEB API**는 웹에서 사용하는 모든 API를 통칭하며, REST API는 WEB API의 한 종류이다.
        - **API 호출 방식** : 마이데이터, 오픈뱅킹 등에서처럼 URL 형태로 API를 호출하여 데이터를 주고받는 방식은 **개인정보의 자동화된 처리**를 가능하게 한다. 이는 개인정보보호법 개정안(데이터 3법)의 가명 처리 특례 규정과도 관련이 있다.
- **자산 식별** : 보안 진단의 첫 단계는 '무엇을 보호할 것인가'를 정의하는 **자산 식별**이다. 클라우드 환경에서는 서버, 데이터베이스뿐 아니라 API, 서버리스 함수, 클라우드 설정 등이 모두 중요한 자산이 된다. 보안 담당자는 **자산의 특징을 명확히 식별하고, 해당 자산에 맞는 보안 가설을 세워 취약점 진단**을 수행해야 한다. 따라서 애플리케이션 개발에 대한 깊은 지식이 필수적이다.

#### API 및 웹 인증
- **API** : 데이터 전송(송수신)을 위한 **오픈된 규격(프로토콜)**이다. 마이데이터 포털과 같이, 여러 기관이 데이터를 안전하게 주고받기 위해 API를 사용한다.
- **쿠키와 개인정보**
    - **개념** : 쿠키는 웹사이트가 사용자의 컴퓨터에 저장하는 작은 데이터 파일이다.
    - **개인정보 여부** : 엄밀히 말해 쿠키는 **개인정보의 일환인 '행태 정보'**에 해당한다. 사용자의 웹사이트 방문 기록, 검색 기록 등을 담고 있다.
    - **보호 필요성** : 현재 우리나라에서는 쿠키를 소극적으로 보호하고 있지만, 개인정보보호법 개정안에 따라 **행태정보 보호법**이 계류 중이며, 쿠키도 보호 대상이 될 것이다. 이는 빅테크 기업들이 초개인화 마케팅에 활용하는 타겟팅 데이터의 보호를 강화하려는 목적이 있다.
- **쿠키의 보안 문제**
    - **재사용 가능성** : 쿠키는 클라이언트(브라우저)에 저장되므로, **탈취되면 누구나 재사용**할 수 있다.
    - **쿠키 하이재킹** : 공격자가 쿠키를 가로채서 사용자의 세션을 탈취하는 공격이다.
    - **결론** : 쿠키는 보안상 취약점이 많아 **민감한 정보를 담는 용도로 사용하지 않는 것이 좋다.**
- **쿠키 기반 웹 인증 방식의 대안**
    - **세션(쿠키) 기반 방식** : 클라이언트에는 **세션 ID**가 담긴 쿠키만 저장하고, 실제 사용자 상태 정보는 **서버의 세션 스토어**에 저장하는 방식이다. 쿠키 하이재킹 공격에 대해 직접적인 정보 유출은 막을 수 있지만, 세션 ID 탈취 시 **세션 하이재킹**에 노출될 수 있다.
    - **토큰 기반 방식(JWT, JSON Web Token)** : **토큰**이라는 일회용 값에 사용자 정보를 담고, **서버의 비밀키로 전자서명을 하여 토큰의 위변조를 방지**한다. 클라이언트는 이 토큰을 매 요청마다 헤더에 담아 보낸다. 서버는 토큰의 서명을 검증하여 유효성을 확인한다. 이는 **무상태(Stateless)** 방식의 인증으로, 서버가 세션 정보를 유지할 필요가 없어 서버리스 환경 등에 적합하며, 보안상 더 안전한 대안으로 여겨진다.

#### 모의 해킹과 상상력
모의 해킹은 시스템의 취약점을 선제적으로 찾아내는 보안 활동이다.
- **외부(No Secure) vs. 내부(Secure)** : 모의 해킹은 일반적으로 **외부(클라이언트 환경)**에서 **내부(서버망)**로의 침투를 시도한다. 이는 외부와 내부를 구분 짓는 **망분리**와 같은 경계 기반 보안의 유효성을 검증하는 과정이기도 하다.
- **ASM (Attack Surface Management)** : 공격 표면을 관리하는 ASM은 **자동화된 취약점 점검**에 효과적이다. 모의 해킹 전문가들이 사용하는 **체크리스트(족보)** 기반의 정형화된 데이터를 학습하면, AI나 자동화된 스캐너가 반복적인 취약점 진단을 수행할 수 있다.
- **상상력과 시나리오 기반 모의 해킹** : 하지만 자동화된 진단만으로는 예측 불가능한 사고를 막기 어렵다. 따라서 **'상상력과 창의성을 기반으로 한 시나리오 모의 해킹'**이 중요하다.
    - **예시** : 단순히 SQL 인젝션 취약점이 있는지 확인하는 것을 넘어, '피싱 이메일로 직원의 계정을 탈취한 후, 내부망에 침투하여 중요 문서를 유출한다'와 같은 **현실적인 공격 시나리오**를 구성하고, 이를 실제로 시뮬레이션하여 시스템의 방어 능력을 종합적으로 평가한다.
- **결론** : 앞으로 모의 해커가 생존하기 위해서는 **체크리스트를 넘어선 해커의 상상력**을 통해 시나리오 기반의 모의 해킹을 수행할 수 있는 역량이 필수적일 것이다.

#### 자바 스크립트와 모바일 앱: 클라이언트 보안의 중요성
- **자바스크립트의 위험성** : 자바스크립트는 클라이언트(브라우저)에서 실행되므로, **의도하지 않은 동작**이 발생하거나 **소스 코드가 변조**될 수 있다.
    - **피싱** : 가짜 모바일 웹 앱을 통해 사용자의 개인 정보를 탈취하는 QR 피싱, 바코드 피싱 등이 대표적인 예이다.
    - **워터링홀(Watering Hole) 공격** : 공격자가 특정 단체가 자주 방문하는 웹사이트(예: 외교부 직원이 방문하는 구호단체 사이트)의 취약점을 미리 심어놓고, 방문자가 접속하는 순간 악성코드가 자동으로 다운로드되도록 하는 공격이다. 보안이 강력한 외교부 직원을 직접 공격하는 대신, 관리 부실한 협력사 사이트를 우회하는 창의적인 공격 시나리오이다.
- **설치에 따른 모바일 앱의 구분**
    - **네이티브 앱** : iOS/안드로이드 개발 언어로 만든 앱. 스토어를 통해 설치하며, 카메라, 마이크 등 **하드웨어 커널(시스템 콜)**에 직접 접근할 수 있어 고도화된 기능 구현이 가능하다. (예: 카카오톡)
    - **모바일 웹 앱** : 웹 기술(HTML5, CSS, 자바스크립트)로 만든 앱. 스토어 설치가 필요 없고, 웹 브라우저에서 실행되므로 **하드웨어 접근에 제한**이 있다. (예: `m.naver.com`)
    - **하이브리드 앱** : 네이티브 앱의 컨테이너 안에 웹 앱을 실행시키는 방식이다. 웹 기술로 대부분의 화면을 구성하면서, 필요한 경우 **하드웨어 접근 권한**을 얻어 네이티브 기능(음성 검색, 카메라 등)을 사용할 수 있다.
    - **클라우드 네이티브 앱** : 클라우드 환경에서 개발된 하이브리드 앱을 의미한다.
- **모바일 웹앱의 증가** : 설치 부담이 없고 개발이 용이한 모바일 웹앱이 증가하는 추세이며, 금융 거래의 빈도가 웹에서 앱으로 빠르게 이동하고 있다. 이는 **애플리케이션 보안의 무게중심이 웹에서 모바일 앱으로 이동**하고 있음을 의미한다.

### 추가 학습 내용: "디지털 플랫폼 정부"와 "세일즈포스 워크플로우 빌더"
- **디지털 플랫폼 정부** : 정부의 행정 서비스를 클라우드 기반의 **디지털 플랫폼** 위에서 제공하고, 여러 부처의 데이터를 연계하여 국민 편의를 높이겠다는 정책이다.
- **세일즈포스 워크플로우 빌더** : 세일즈포스(Salesforce)와 같은 클라우드 기반 SaaS 플랫폼에서, 사용자가 직접 코딩 없이도 복잡한 **업무 자동화(워크플로우)**를 만들 수 있게 돕는 도구이다.
- **보안 관점에서의 연관성** : 이 두 가지는 모두 **클라우드와 SaaS 기반의 업무 환경 확산**을 보여주는 사례이다. 이러한 환경에서는 전통적인 경계 보안만으로는 한계가 있기 때문에 **'디지털 플랫폼 정부 3단계 보안'**과 같이, **클라우드 네이티브 환경에 특화된 보안, 데이터 연계에 따른 개인 정보 보호, SaaS 사용에 대한 접근 제어 및 설정 오류 방지** 등 새로운 보안 정책과 기술이 요구된다.

### 오후 토론: 망분리 완화

#### 1. 망분리 완화의 배경 및 정책 요약
- **공통된 배경** : 금융권, 공공기관, 개인정보보호위원회 모두 **생성형 AI, 클라우드(SaaS) 같은 신기술을 활용**하여 업무 효율을 높이고 혁신을 촉진하기 위해 기존의 경직된 망분리 규제를 완화하고 있다.
- **정책의 핵심 변화**
    - **'무조건 차단' → '위험도 기반 차등 적용'** : 모든 시스템을 동일하게 다루는 것이 아니라, 데이터의 중요도나 위험도에 따라 망 분리 수준을 다르게 적용한다.
    - **'규제 중심' → '자율과 책임 중심'** : 금융권에서는 행위 규칙(Rule) 중심의 규제를 목표(Principle) 중심으로 전환하고, 공공기관은 다층보안체계(MLS)를 차세대 보안(N²SF)으로 전환하려는 움직임을 보이고 있다. 이는 각 기관이 자체적으로 리스크를 평가하고 책임지고 보안을 강화하는 방향으로 변화하고 있음을 의미한다.

#### 2. 망분리 완화에 따른 추가 보안 조치
망분리 완화가 단순히 보안 규제를 없애는 것이 아니라, 오히려 **새로운 보안 패러다임**을 요구한다는 점을 명확히 하고 있다.
- **자율보안 및 결과 책임** : 기업이나 기관이 스스로 보안 대책을 수립하고, 그 결과에 책임을 지는 원칙이 강화된다.
- **위험도 기반 차등화** : 모든 망을 동일하게 취급하지 않고, 중요도에 따라 차등적으로 보안 등급을 매겨 관리한다.
- **제로 트러스트(Zero Trust)** : "절대 신뢰는 없다"는 원칙에 따라, 내부망이라도 모든 접속에 대해 인증과 권한을 엄격하게 확인하는 시스템이 필수적이다.
- **신기술 솔루션 도입** : **DLP(데이터 유출 방지)**, **CDR(콘텐츠 무해화)**, **AI 기반 탐지 솔루션** 등 망분리가 사라진 환경에서 데이터와 위협을 효과적으로 관리할 수 있는 기술들이 중요해질 것이다.
- **강화된 감사 체계** : 실시간으로 모든 활동을 기록(로깅)하고, 내부 감사 체계를 강화하여 보안 사고 발생 시 원인을 파악하고 대응할 수 있는 시스템을 구축해야 한다.

#### 3. 보안 담당자의 대응 전략
망분리 완화 시대에 보안 담당자가 실질적으로 실행해야 할 구체적인 전략을 제시하고 있다.
- **제로 트러스트 구조 설계** : 외부와의 경계가 사라진 환경에서 사용자 인증, 최소 권한 원칙, 세션 감시를 통해 내부의 모든 접근을 통제해야 한다. 특히 AI나 SaaS 같은 외부 서비스 접근 시 **VPN/ZTNA**를 활용하고 **다단계 인증(MFA)**을 의무화해야 한다.
- **데이터 중심의 보호** : 데이터 자체가 유출되거나 변조되지 않도록 **가명화, 암호화**를 적용하는 것이 중요하다. 특히 AI와 연계될 경우, 데이터 이동 경로에 대한 **DLP/CDR 로깅**을 필수로 구축해야 한다.
- **내부 운영 체계 강화** : 망분리 완화는 '자율성'을 부여하는 대신 '책임'을 요구하는 것이므로, 정기적인 위험 분석과 등급 분류를 통해 보안 수준을 지속적으로 점검하고 개선해야 한다. 책임자를 지정하고, 재평가 및 감사 시스템을 구축하여 보안 체계를 견고하게 운영해야 한다.

#### 결론
- 모든 보안 규제 변화에는 이유가 있다.
- 규제는 추상적이고 모호하지만, 전문가는 구체적이고 명확한 계획을 세워야 한다.
