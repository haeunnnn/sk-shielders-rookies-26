## 🧠 주요 개념 정리

### 1. AWS (Amazon Web Service)

#### AWS (Amazon Web Service)
- 아마존닷컴에서 제공하는 클라우드 컴퓨팅 플랫폼 및 서비스의 집합
- 인터넷을 통해 서버, 스토리지, 데이터베이스, 네트워킹 등 다양한 IT 인프라와 소프트웨어, 플랫폼을 필요한 만큼 빌려 쓰고 사용한 만큼만 비용을 지불하는 방식

**AWS의 **주요 특징** 및 장점**
- **비용 효율성** : 물리적인 서버를 직접 구매하고 유지 관리하는 대신, 사용한 만큼만 비용을 지불하는 **종량제 모델**이라 초기 투자 비용이 적고 효율적인 비용 관리가 가능하다.
- **확장성 및 유연성** : 비즈니스 요구에 따라 컴퓨팅 자원을 쉽고 빠르게 늘리거나 줄일 수 있다. 트래픽이 많을 때는 자동으로 서버를 늘리고, 적을 때는 줄여 효율적으로 자원을 활용할 수 있다.
- **높은 가용성 및 안정성** : 전 세계에 분산된 데이터 센터를 통해 서비스를 제공하므로, 특정 지역에 문제가 발생하더라도 서비스 중단 없이 안정적으로 운영할 수 있다.
- **다양한 서비스** : 컴퓨팅, 스토리지, 데이터베이스는 물론 인공지능/머신러닝, IoT, 보안, 분석 등 200가지가 넘는 방대한 서비스를 제공하여 거의 모든 종류의 애플리케이션과 워크로드를 구축하고 운영할 수 있다.
- **보안** : 강력한 보안 기능과 규정 준수 기능을 제공하여 데이터와 애플리케이션을 안전하게 보호할 수 있다.

### 2. 클라우드 컴퓨팅의 기본 개념 이해

#### 클라우드 컴퓨팅의 장점 (온프레미스와의 비교)
- **온프레미스(On-premise)**는 기업이 자체 데이터 센터에 서버, 스토리지, 네트워크 장비 등을 직접 구매하고 설치하며 유지 관리하는 방식이다.

| 특징 | **클라우드 컴퓨팅 (AWS)** | **온프레미스** |
| --- | ------------------- | -------- |
| 초기 비용 | 낮음: 하드웨어 구매 비용 없음. 사용한 만큼 지불 | 높음: 서버, 스토리지 등 대규모 초기 투자 필요 |
| 운영 비용 | 유연한 종량제, 인력 비용 절감 | 장비 유지보수, 전력, 냉방, 전담 인력 등 지속적인 비용 |
| 확장성 | 높음: 필요에 따라 몇 분 만에 자원 확장/축소 가능 | 낮음: 자원 확장 시 추가 구매 및 설치 시간 소요 |
| 유연성 | 다양한 서비스와 기술 스택 선택 가능 | 기존 인프라에 제약이 많음 |
| 가용성 | 높음: 여러 지역/데이터 센터에 분산, 재해 복구 용이 | 단일 데이터 센터 의존, 재해 시 취약 |
| 속도 | 몇 분 안에 인프라 프로비저닝 가능 | 장비 구매, 설치, 설정에 수주 ~ 수개월 소요 |
| 관리 책임 | AWS가 인프라 관리, 사용자는 애플리케이션에 집중 | 모든 인프라 및 소프트웨어 관리 책임 |
| 보안 | AWS의 강력한 글로벌 보안 인프라 활용 | 기업 자체 보안 역량에 의존 |

**핵심 장점**
- **비용 효율성** : 더 이상 값비싼 하드웨어를 구매하고 유지보수할 필요가 없다. 사용한 만큼만 지불하는 **종량제(Pay-as-you-go)** 모델이라 초기 투자 비용이 적고, 사용량에 따라 유연하게 비용을 조절할 수 있다.
- **민첩성 및 확장성** : 비즈니스 요구사항에 따라 몇 분 만에 서버나 스토리지를 추가하거나 줄일 수 있다. 갑작스러운 트래픽 증가에도 유연하게 대응할 수 있어 서비스 중단을 최소화하고 고객에게 안정적인 경험을 제공한다.
- **운영 부담 감소** : 서버 관리, 네트워크 설정, 보안 패치 등 번거로운 인프라 관리 작업을 AWS가 대신 처리해주므로, 기업은 핵심 비즈니스 로직 개발과 혁신에 더 집중할 수 있다.
- **글로벌 인프라 활용** : AWS의 전 세계에 분산된 데이터 센터를 활용하여 전 세계 사용자에게 낮은 지연 시간으로 서비스를 제공하고, 재해 복구 계획을 손쉽게 구축할 수 있다.

#### IaaS, PaaS, SaaS와 같은 클라우드 서비스 모델 이해
클라우드 서비스는 제공되는 관리 수준에 따라 크게 세 가지 모델로 나뉩니다. 각 모델은 사용자가 직접 관리해야 하는 부분과 클라우드 공급자(AWS)가 관리하는 부분의 범위가 다르다.

**IaaS (Infrastructure as a Service: 서비스형 인프라)**
- **정의** : 가장 기본적인 클라우드 서비스 모델로, 클라우드 공급자가 네트워킹, 가상 서버(VM), 스토리지 등 핵심 IT 인프라를 가상화하여 제공한다. 빈 땅 위에 건물을 짓는 것과 같다.
- **관리 책임**
    - **클라우드 공급자 (AWS)** : 물리적 서버, 스토리지, 네트워킹, 가상화 계층 관리
    - **사용자** : 운영체제, 미들웨어, 런타임, 데이터, 애플리케이션 관리 (가장 많은 관리 책임)
- **주요 특징**
    - 높은 유연성과 제어권을 제공한다.
    - 온프레미스 환경과 가장 유사하며, 기존 애플리케이션을 클라우드로 마이그레이션하기 용이하다.
- **AWS 서비스 예시** : Amazon EC2 (가상 서버), Amazon S3 (스토리지), Amazon VPC (네트워크)

**PaaS (Platform as a Service: 서비스형 플랫폼)**
- **정의** : IaaS 위에 운영체제, 런타임 환경, 데이터베이스, 웹 서버 등 애플리케이션 개발 및 실행에 필요한 플랫폼을 추가로 제공한다. 개발자는 인프라 관리 없이 코드만 배포하면 된다. 건물의 뼈대와 필수 설비가 갖춰진 상태에서 인테리어만 하는 것과 같다.
- **관리 책임**
    - **클라우드 공급자 (AWS)** : 물리적 인프라, 운영체제, 미들웨어, 런타임 관리
    - **사용자** : 애플리케이션 코드 및 데이터 관리
- **주요 특징**
    - 개발 생산성이 크게 향상된다.
    - 인프라 설정 및 관리에 대한 부담이 줄어든다.
- **AWS 서비스 예시** : AWS Elastic Beanstalk (애플리케이션 배포 및 관리 플랫폼), AWS Lambda (서버리스 함수), Amazon RDS (관리형 데이터베이스)

**SaaS (Software as a Service: 서비스형 소프트웨어)**
- **정의** : 클라우드 공급자가 모든 소프트웨어와 인프라를 호스팅하고 관리하며, 사용자는 단순히 웹 브라우저나 모바일 앱을 통해 소프트웨어를 이용한다. 완공된 건물을 빌려 쓰는 것과 같다.
- **관리 책임**
    - **클라우드 공급자 (AWS)** : 모든 인프라, 플랫폼, 소프트웨어 관리 및 유지보수
    - **사용자** : 소프트웨어 사용 (가장 적은 관리 책임)
- **주요 특징**
    - 가장 쉽고 빠르게 소프트웨어를 사용할 수 있다.
    - 설치나 유지보수가 필요 없어 최종 사용자에게 편리하다.
- **AWS 서비스 예시** (AWS 자체 서비스 중 SaaS 형태는 많지 않지만) : Amazon Chime (화상 회의), Amazon WorkMail (이메일 서비스), 또는 AWS Marketplace를 통해 제공되는 써드파티 소프트웨어들이 SaaS 형태가 많다. 일반적으로 우리가 쓰는 Gmail, Dropbox, Salesforce 등이 대표적인 SaaS이다.

#### AWS 리전(Region)과 가용 영역(Availability Zone, AZ)의 개념
AWS 클라우드가 전 세계적으로 안정적이고 높은 성능을 제공할 수 있는 핵심적인 인프라 구성 요소이다.

**리전 (Region)**
- **정의** : AWS 서비스가 호스팅되는 지리적으로 독립적인 물리적 위치이다. 전 세계 주요 대도시에 분산되어 있다. 각 리전은 완전히 독립적이며, 다른 리전의 장애에 영향을 받지 않는다.
- **예시** : 서울 리전 (ap-northeast-2), 버지니아 북부 리전 (us-east-1), 도쿄 리전 (ap-northeast-1) 등
- **선택 기준**
    - **지연 시간 (Latency)** : 사용자 위치와 가까운 리전을 선택하여 서비스 응답 속도를 향상시킨다. 한국 사용자는 일반적으로 서울 리전(ap-northeast-2)을 선택하는 것이 유리하다.
    - **규정 준수 및 데이터 주권** : 특정 국가 또는 지역의 데이터 저장 규정(예: GDPR)을 준수해야 할 경우 해당 지역 내 리전을 선택해야 한다.
    - **비용** : 리전별로 서비스 비용이 약간 다를 수 있다.
    - **제공 서비스** : 특정 서비스는 모든 리전에서 제공되지 않을 수 있으므로, 필요한 서비스가 해당 리전에 있는지 확인해야 한다.
- **특징**
    - 각 리전은 다른 리전과 완벽하게 격리되어 있어, 한 리전에 재해가 발생해도 다른 리전에 영향을 미치지 않는다.
    - 리전 간 데이터 전송에는 비용이 발생하며, 네트워크 지연도 발생할 수 있다.

**가용 영역 (Availability Zone, AZ)**
- **정의** : 각 리전은 하나 이상의 **가용 영역(AZ)**으로 구성된다. AZ는 리전 내에서 물리적으로 분리된, 독립적인 데이터 센터 클러스터이다. 각 AZ는 자체적인 전력, 네트워킹, 냉각 시스템을 갖추고 있다.
    - **예시** : 서울 리전 (ap-northeast-2)은 ap-northeast-2a, ap-northeast-2b, ap-northeast-2c와 같은 여러 AZ로 구성된다.
- **선택 기준**
    - **고가용성 (High Availability)** : 애플리케이션의 안정성을 높이기 위해 여러 AZ에 걸쳐 리소스를 분산 배치하는 것이 좋다. 한 AZ에 문제가 생겨도 다른 AZ의 리소스가 서비스를 계속 제공할 수 있기 때문이다.
    - **내결함성 (Fault Tolerance)** : AZ 간의 물리적 분리 덕분에, 지진, 홍수, 정전 등 단일 데이터 센터에 영향을 미치는 장애로부터 서비스를 보호할 수 있다.
- **특징**
    - 동일 리전 내의 AZ 간에는 매우 빠르고 저렴하며 낮은 지연 시간의 네트워크 연결이 보장된다.
    - 각 AZ는 다른 AZ와 독립적으로 운영되므로, 한 AZ의 장애가 다른 AZ에 영향을 주지 않는다.

**리전과 가용 영역의 중요성**
AWS를 이용하여 서비스를 구축할 때, 리전과 AZ의 개념을 이해하고 적절히 활용하는 것은 고가용성, 내결함성, 재해 복구(Disaster Recovery) 전략을 수립하는 데 매우 중요하다. 예를 들어, 웹 서버를 여러 AZ에 분산 배치하고, 데이터베이스도 다중 AZ로 구성하면 특정 데이터 센터에 문제가 발생해도 서비스가 중단 없이 계속될 수 있다.

### 3. EC2

#### EC2 (Elastic Compute Cloud)
AWS 실습에서 가장 먼저 접하게 되는 서비스 중 하나가 **EC2(Elastic Compute Cloud)**이다. 이름 그대로 "탄력적인 컴퓨팅 클라우드"라는 의미를 가지고 있다.

쉽게 말해, EC2는 AWS 클라우드에서 제공하는 가상 서버라고 생각하면 된다. 온프레미스(On-premise) 환경에서 물리적인 컴퓨터를 구매해서 운영체제를 설치하고 필요한 소프트웨어를 구동하는 것과 비슷하다. 하지만 EC2는 이 모든 과정이 AWS 클라우드 내에서 가상화되어 이루어지는 것.

#### EC2의 주요 특징

1. **애플리케이션 및 OS 이미지 (AMI: Amazon Machine Image)**
- AMI는 EC2 인스턴스를 시작하는 데 필요한 정보를 담고 있는 템플릿이다. 여기에는 운영체제(OS), 애플리케이션 서버, 애플리케이션 등이 미리 구성되어 있다. 마치 컴퓨터를 살 때 윈도우나 리눅스가 미리 깔려있는 것과 같다.

2. **인스턴스 유형 (Instance Type)**
- 인스턴스 유형은 EC2 인스턴스의 하드웨어 구성(CPU, 메모리, 스토리지, 네트워크 성능)을 정의한다. 마치 다양한 성능의 노트북 모델을 고르는 것과 같다. 웹 서버, 데이터베이스 서버, 고성능 컴퓨팅 등 용도에 따라 적합한 유형을 선택할 수 있다.

3. **네트워크 설정 (VPC: Virtual Private Cloud)**
- VPC는 AWS 클라우드 내에 사용자를 위한 논리적으로 격리된 가상 네트워크를 의미한다. 마치 AWS 데이터센터 안에 나만의 사설 네트워크 공간을 만드는 것과 같다. 여기에서 IP 주소 범위, 서브넷, 라우팅 테이블 등을 직접 정의할 수 있다.

4. **자동 퍼블릭 IP 할당**
- EC2 인스턴스가 인터넷에 직접 연결되기 위해 필요한 공인 IP 주소를 자동으로 할당받는 설정이다. 이 퍼블릭 IP 주소를 통해 외부에서 인스턴스에 접근(예: SSH 접속, 웹사이트 접속)할 수 있게 된다.

5. **SSH 연결** (`ssh -i mykp01.pem ec2-user@[퍼블릭IP주소]`)
- SSH(Secure Shell)는 원격 컴퓨터에 안전하게 접속하기 위한 프로토콜이다. EC2 인스턴스는 대부분 GUI(Graphical User Interface) 없이 명령줄(CLI) 환경으로 운영되기 때문에, SSH를 통해 원격으로 접속하여 명령어를 실행하고 설정 작업을 한다.

## 💻 실습 내용

### 실습 주제 1: 간단한 EC2 인스턴스 생성해보기
- 콘솔 > EC2 > 인스턴스 > 인스턴스 시작
    - **애플리케이션 및 OS 이미지(AMI)** : `Amazon Linux2023`
        - AWS에서 최적화하고 제공하는 리눅스 운영체제 이미지이다. 이 AMI를 선택하면 해당 OS가 설치된 가상 서버가 생성되는 것이다. 특정 웹 서버나 데이터베이스가 미리 설치된 AMI도 있어서 개발 환경을 빠르게 구축할 수 있다.
    - **인스턴스 유형** : `t3.micro`
        - **프리티어(Free Tier)**에서 일정 시간 무료로 사용할 수 있는 가장 기본적인 유형 중 하나. 개발/테스트용이나 트래픽이 적은 웹사이트에 적합하다. 't' 시리즈는 버스터블(Burstable) 성능을 제공하여, 평소에는 낮은 CPU를 사용하다가 필요할 때 순간적으로 성능을 높일 수 있는 특징이 있다.
    - **네트워크 설정** : Default VPC (없으면 네트워크 환경 만들기)
        - AWS 계정을 만들면 기본적으로 설정되어 있는 VPC이다. 이 VPC 내에서 EC2 인스턴스가 생성되고 인터넷에 연결될 수 있는 환경이 구성된다. 만약 없었다면 직접 네트워크 환경을 만들어야 했을 것이다.
    - **자동 퍼블릭 IP 할당** : 활성화
    - EC2 생성 후, 상세 내용 살펴보기
- 해당 인스턴스 체크 후 **인스턴스 종료(삭제)**
    - EC2 인스턴스를 더 이상 사용하지 않을 때 이를 완전히 삭제하는 과정이다. 단순히 중지(Stop)하는 것과 달리, 종료(Terminate)하면 모든 데이터가 사라지고 다시 시작할 수 없으니 잘 확인하자.
    - **비용 발생을 막기 위해 실습 후에는 반드시 인스턴스를 종료(삭제)하는 것이 중요하다**. 중지 상태로 두면 스토리지 비용 등 일부 비용이 계속 발생할 수 있다.

### 실습 주제 2: EC2 인스턴스 생성 및 ssh 연결해보기
- git bash에 ` ssh -i mykp01.pem ec2-user@[퍼블릭IP주소]` 입력하여 ssh 연결
    - `-i mykp01.pem` : mykp01.pem은 인스턴스 생성 시 다운로드받은 키 페어(Key Pair) 파일이에요. 이 파일은 인스턴스에 접근하기 위한 보안 인증서 역할을 합니다. 공개 키는 EC2 인스턴스에, 개인 키는 사용자 컴퓨터에 저장되어 서로 인증하는 방식이죠.
    - `ec2-user` : Amazon Linux 계열 AMI의 기본 사용자 이름이에요. 다른 리눅스 AMI(예: Ubuntu)는 ubuntu와 같은 다른 기본 사용자 이름을 가질 수 있어요.
    - `[퍼블릭IP주소]` : 위에서 언급한, EC2 인스턴스에 할당된 공인 IP 주소예요. 이 주소를 통해 인터넷에서 인스턴스를 찾아 접속하게 됩니다.


EC2는 AWS 클라우드에서 가장 기본적인 컴퓨팅 자원이며, 대부분의 웹 서비스나 애플리케이션의 기반이 된다. 이 실습을 통해 가상 서버를 만들고, 접속하고, 관리하는 기본적인 과정을 경험할 수 있었다.

## ❓ 궁금한 점

- **애플리케이션을 AWS에 배포한다고 가정할 때, IaaS와 PaaS 중 어떤 상황에서 어떤 모델을 선택하는 것이 더 효율적일지 구체적인 시나리오를 들어 설명해볼 수 있을까?**
    - **IaaS 선택 시나리오** : 레거시(Legacy) 애플리케이션을 클라우드로 그대로 마이그레이션해야 하거나, 운영체제부터 미들웨어, 런타임 환경까지 완벽한 제어권이 필요한 경우. 또는 특정 보안 규정 준수를 위해 커스텀 설정이 필수적인 경우
    - **PaaS 선택 시나리오** : 빠르게 애플리케이션을 개발하고 배포해야 하며, 인프라 관리 부담을 최소화하고 개발 자체에 집중하고 싶은 경우. 서버 관리, 패치, 스케일링 등을 AWS가 자동으로 처리해주길 원할 때.
- **클라우드보다는 온프레미스 환경이 우선시 되는 시나리오는 뭐가 있을까?**
    - **매우 엄격한 규제 및 데이터 주권 요구사항** : 금융, 공공, 국방 등 특정 산업에서 데이터가 반드시 물리적으로 특정 국가나 기업 내부 시설에만 존재해야 한다는 극도로 엄격한 규제가 있을 때. 클라우드 서비스가 해당 규정을 100% 만족시키기 어려운 경우
    - **초고성능/저지연 요구사항 및 기존 투자 활용** : 데이터 센터 내의 장비 간 초저지연(Ultra-low latency) 통신이 필수적이거나, 이미 대규모의 온프레미스 인프라에 막대한 투자를 하여 충분히 활용하고 있는 경우. 클라우드로의 전환 비용이 기존 인프라 유지 비용보다 훨씬 더 클 수 있음.
    - **예측 가능한 대규모 고정 워크로드** : 서비스 수요가 매우 안정적이고 예측 가능하며, 장기간 고정된 대규모 컴퓨팅 자원이 필요한 경우. 클라우드의 유연한 종량제 모델보다 직접 인프라를 소유하는 것이 장기적으로 더 비용 효율적일 수 있음
