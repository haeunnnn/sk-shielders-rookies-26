## 🧠 주요 개념 정리

### 1. 데이터베이스 서버 준비하기

애플리케이션이 데이터를 저장하고 관리하려면 데이터베이스 서버가 필요하다. AWS는 다양한 데이터베이스 서비스를 제공하여 사용자의 필요에 맞춰 선택할 수 있도록 돕는다.

#### 데이터베이스 서버란

데이터를 체계적으로 저장, 관리, 검색하는 소프트웨어 시스템을 실행하는 서버를 말한다. 웹 애플리케이션, 모바일 앱, 비즈니스 시스템 등 대부분의 현대적인 애플리케이션은 데이터베이스를 통해 정보를 영구적으로 저장하고 활용한다.

#### 데이터베이스 종류

데이터베이스는 크게 두 가지 주요 카테고리로 나뉜다: **관계형 데이터베이스(SQL)**와 **비관계형 데이터베이스(NoSQL)**.

- **관계형 데이터베이스 (Relational Database, SQL)**
    - **정의**: 테이블, 행, 열의 형태로 데이터를 구조화하고, 미리 정의된 스키마에 따라 데이터를 저장한다. 테이블 간의 관계를 `JOIN`과 같은 SQL(Structured Query Language)을 사용하여 정의하고 질의한다.
    - **특징**: 데이터의 **정합성(일관성)**과 **무결성**을 강력하게 보장하며, 복잡한 쿼리에 효율적이다.
    - **예시**: MySQL, PostgreSQL, Oracle, SQL Server, MariaDB 등.
- **비관계형 데이터베이스 (Non-Relational Database, NoSQL)**
    - **정의**: 관계형 모델을 사용하지 않고 다양한 방식으로 데이터를 저장하고 관리한다. 유연한 스키마를 가지며 대용량 데이터 처리 및 고속 읽기/쓰기에 최적화되어 있다.
    - **특징**: 유연한 데이터 모델링, 수평적 확장(Scale-out) 용이, 빠른 성능.
    - **종류 및 예시**:
        - **키-밸류 스토어 데이터베이스**: 데이터를 고유한 키와 해당 값의 쌍으로 저장한다. 가장 단순한 형태의 NoSQL이며, 고속 접근이 필요할 때 사용한다. (예: **Amazon DynamoDB**, Redis)
        - **문서 기반 데이터베이스**: JSON, BSON, XML과 같은 반정형(Semi-structured) 문서를 저장한다. 유연한 스키마를 가지며, 문서 형태의 데이터를 다룰 때 유용하다. (예: MongoDB, **Amazon DocumentDB**)
        - **그래프 데이터베이스**: 엔티티(노드)와 그 관계(엣지)를 그래프 형태로 저장하여 복잡한 관계 질의에 최적화되어 있다. (예: **Amazon Neptune**)
        - **와이드 컬럼 스토어**: 행과 열을 유연하게 정의하며, 대규모 분산 데이터에 효율적이다. (예: Apache Cassandra, **Amazon Keyspaces**)

#### Amazon RDS (Relational Database Service)

**Amazon RDS**는 클라우드에서 관계형 데이터베이스를 쉽게 **설정, 운영, 확장**할 수 있도록 돕는 관리형 서비스이다. 사용자가 직접 데이터베이스 서버를 설치하고 관리할 필요 없이, AWS가 대부분의 운영 작업을 대신 처리한다.

#### 관리형 서비스와 비관리형 서비스

- **관리형 서비스 (Managed Service)**: AWS가 하드웨어 프로비저닝, OS 패치, 데이터베이스 설치, 백업, 복구, 확장 등 대부분의 운영 및 유지보수 작업을 담당한다. 사용자는 애플리케이션과 데이터베이스 스키마 개발에만 집중할 수 있다. **Amazon RDS, Amazon DynamoDB**가 대표적인 관리형 서비스이다.
- **비관리형 서비스 (Unmanaged Service)**: 사용자가 직접 EC2 인스턴스에 데이터베이스를 설치하고 모든 운영 및 유지보수 작업을 책임진다. 더 많은 제어권을 가지지만, 운영 부담이 크다. **EC2에 MySQL을 직접 설치**하는 경우가 비관리형 서비스의 예시이다.

#### RDS 인스턴스 클래스

RDS 인스턴스 클래스는 데이터베이스 서버의 **하드웨어 사양**을 정의한다. CPU, 메모리, 네트워크 성능 등을 기준으로 다양한 클래스를 제공하며, 워크로드에 맞춰 선택한다. EC2 인스턴스 유형과 유사하다. (예: `db.t3.micro`, `db.m5.large`)

#### Multi-AZ (다중 AZ)

RDS의 **고가용성 및 재해 복구**를 위한 기능이다. 데이터베이스 인스턴스를 주(Primary) AZ와 보조(Standby) AZ에 **동기적으로 복제**하여 배포한다. 주 인스턴스에 장애가 발생하면 자동으로 보조 인스턴스로 전환되어 서비스 중단을 최소화한다.

#### 읽기 전용 복제본 (Read Replica)

데이터베이스의 **읽기 성능 확장**을 위한 기능이다. 원본(Primary) 데이터베이스의 데이터를 **비동기적으로 복제**하여 여러 개의 읽기 전용 인스턴스를 생성한다. 애플리케이션의 읽기 요청을 이 복제본들로 분산시켜 원본 데이터베이스의 부하를 줄인다. 쓰기 작업은 항상 원본 데이터베이스에서만 이루어진다.

#### RDS 접근 제어 (NACL과 Security Group을 이용한 접근 제어)

RDS 인스턴스에 대한 네트워크 접근을 안전하게 제어하는 것은 매우 중요하다.

- **보안 그룹 (Security Group)**: RDS 인스턴스 수준에서 가상 방화벽 역할을 한다. 인바운드/아웃바운드 트래픽에 대해 `허용(Allow)` 규칙을 정의하여, 특정 IP 주소나 다른 보안 그룹의 인스턴스(예: EC2 웹 서버)만 데이터베이스에 접근하도록 설정한다.
- **NACL (Network Access Control List)**: 서브넷 수준에서 패킷 필터링을 수행하는 방화벽이다. 보안 그룹보다 상위 개념으로, `허용(Allow)`과 `거부(Deny)` 규칙을 모두 정의할 수 있다. RDS 인스턴스가 위치한 서브넷에 적용되어 추가적인 보안 계층을 제공한다.

#### RDS 데이터베이스 백업

RDS는 데이터 손실을 방지하고 복구를 용이하게 하기 위해 두 가지 주요 백업 방식을 제공한다.

- **자동 백업 (Automated Backups)**: 사용자가 설정한 백업 보존 기간(1~35일) 동안 데이터베이스의 특정 시점(Point-in-time) 복구를 가능하게 한다. 매일 자동으로 스냅샷을 찍고 트랜잭션 로그를 기록하여 원하는 시점으로 복구할 수 있다.
- **DB 스냅샷 (DB Snapshots)**: 사용자가 수동으로 생성하는 백업이다. 원하는 시점에 데이터베이스의 전체 스냅샷을 만들고 S3에 저장한다. 자동 백업과 달리 무기한 보존할 수 있으며, 다른 리전으로 복사하여 재해 복구 계획에 활용할 수 있다.

#### RDS 구성 (실습 과정)

- **파라미터 그룹/옵션 그룹 생성하기**:
    - **파라미터 그룹**: 데이터베이스 엔진의 **런타임 구성 설정**을 관리하는 곳이다. 메모리 할당, 문자열 인코딩, 연결 시간 초과 등 수백 가지의 데이터베이스 파라미터를 조절하여 성능을 최적화할 수 있다. 기본 파라미터 그룹을 사용하거나, 필요에 따라 사용자 정의 파라미터 그룹을 생성한다.
    - **옵션 그룹**: 특정 데이터베이스 기능(예: Oracle TDE, SQL Server Integration Services)을 활성화하거나 데이터베이스와 통합할 때 사용한다.
- **서브넷 그룹 생성하기**:
    - RDS 인스턴스를 배포할 **VPC 내의 서브넷(최소 2개 이상의 AZ에 걸쳐진 서브넷)** 집합을 정의하는 것이다. RDS는 이 서브넷 그룹 내에서 데이터베이스 인스턴스와 Multi-AZ 스탠바이 인스턴스를 자동으로 프로비저닝한다. 고가용성을 위해 반드시 두 개 이상의 AZ에 걸쳐진 서브넷으로 구성해야 한다.
- **데이터베이스 생성하기**:
    - 데이터베이스 엔진, 인스턴스 클래스, 스토리지 크기, 사용자 이름/비밀번호, VPC 및 서브넷 그룹, 보안 그룹 등을 선택하여 RDS 데이터베이스 인스턴스를 생성한다.

#### Amazon DynamoDB

**Amazon DynamoDB**는 AWS에서 제공하는 **빠르고 유연한 NoSQL 데이터베이스 서비스**이다. 키-밸류 및 문서 데이터 모델을 지원하며, 페타바이트 규모의 데이터와 초당 수백만 건의 요청을 처리할 수 있도록 설계된 완전 관리형 서비스이다.

- **정의**: 대규모 분산 환경에서 낮은 지연 시간으로 높은 처리량을 제공하는 NoSQL 데이터베이스이다.
- **특징**:
    - **완전 관리형**: 서버 프로비저닝, 패치, 백업 등 모든 운영 부담을 AWS가 처리한다.
    - **고성능 및 확장성**: 수평적 확장을 통해 거의 무제한의 처리량과 스토리지를 제공하며, 밀리초 단위의 지연 시간을 보장한다.
    - **서버리스**: 서버를 관리할 필요가 없으며, 사용량에 따라 자동으로 확장 및 축소된다.
    - **내구성 및 가용성**: 데이터를 여러 AZ에 자동으로 복제하여 높은 내구성과 가용성을 제공한다.
- **활용**: 웹/모바일 애플리케이션, 게임 백엔드, IoT 데이터, 광고 기술 등 고속 데이터 접근이 필요한 시나리오에 적합하다.

### 2. AWS Lambda

**AWS Lambda**는 서버를 프로비저닝하거나 관리할 필요 없이 코드를 실행할 수 있게 해주는 **서버리스(Serverless) 컴퓨팅 서비스**이다. 개발자는 코드만 작성하고 업로드하면 된다.

#### Lambda란

- **정의**: 이벤트에 응답하여 코드를 실행하고, 자동으로 기본 컴퓨팅 리소스를 관리하는 컴퓨팅 서비스이다. 즉, "서버 없이" 코드를 실행할 수 있게 해준다.
- **컨셉**: 서버를 항상 켜 둘 필요 없이, 특정 이벤트(예: S3에 파일 업로드, API Gateway 요청, DynamoDB 테이블 변경)가 발생할 때만 코드를 실행하고 사용한 컴퓨팅 시간만큼만 비용을 지불한다.

#### Lambda 사용 예시

- **웹 애플리케이션 백엔드**: API Gateway와 연동하여 서버리스 RESTful API를 구축한다.
- **데이터 처리**: S3에 새로운 파일이 업로드될 때 자동으로 이미지 크기를 조정하거나 데이터베이스에 삽입하는 함수를 실행한다.
- **실시간 스트림 처리**: Kinesis 스트림에 데이터가 들어오면 Lambda가 이를 처리한다.
- **챗봇 백엔드**: 챗봇 플랫폼의 사용자 입력에 응답하는 로직을 구현한다.

#### Lambda의 실행

Lambda 함수는 특정 **이벤트 소스(Event Source)**에 의해 트리거(실행)된다.

- **동기식 호출**: 이벤트 소스가 Lambda 함수를 호출하고 응답을 기다린다. (예: API Gateway 요청)
- **비동기식 호출**: 이벤트 소스가 Lambda 함수를 호출하고 응답을 기다리지 않고 계속 진행한다. (예: S3 이벤트)

#### Lambda의 특징

- **서버리스**: 서버를 프로비저닝, 확장, 패치 또는 유지보수할 필요가 없다.
- **이벤트 기반**: 특정 이벤트 발생 시에만 코드가 실행되므로, 유휴 시간 동안 비용이 발생하지 않는다.
- **자동 확장**: 들어오는 이벤트 수에 따라 자동으로 확장 및 축소된다.
- **종량 과금**: 코드가 실행된 컴퓨팅 시간(밀리초 단위)과 호출 횟수에 따라 요금이 부과된다.
- **빠른 시작 시간**: 코드 실행 환경이 미리 준비되어 있어 빠르게 시작될 수 있다.

#### Lambda 실행 역할 (Execution Role)

Lambda 함수가 AWS의 다른 서비스(예: S3, DynamoDB, CloudWatch Logs)에 접근해야 할 때, 해당 함수에게 필요한 권한을 부여하는 **IAM 역할**이다. Lambda 함수를 생성할 때 이 역할을 지정해야 한다. Lambda 함수는 이 역할이 가진 권한을 '가정'하여 AWS 리소스에 접근한다.

### 3. VPC와 다른 네트워크 연결

AWS 클라우드에 구축한 VPC를 온프레미스 데이터센터나 다른 VPC, 또는 다른 AWS 계정의 VPC와 안전하게 연결하는 방법이다.

#### AWS VPN (Virtual Private Network)

**AWS VPN**은 온프레미스 네트워크와 AWS VPC 간에 **보안되고 암호화된 터널(Tunnel)**을 통해 안전한 연결을 설정하는 서비스이다. 인터넷을 통해 통신하지만, 데이터는 암호화되어 전송되므로 외부에서 내용을 볼 수 없다.

- **정의**: 인터넷을 통해 온프레미스 네트워크와 VPC 간에 암호화된 통신 경로를 제공한다.
- **활용**: 온프레미스에서 클라우드로 데이터를 안전하게 전송하거나, 온프레미스 사용자가 VPC 내의 리소스에 안전하게 접근해야 할 때 사용한다.
- **구성 요소**:
    - **Virtual Private Gateway (VGW)**: VPC 측의 VPN 연결 엔드포인트.
    - **Customer Gateway (CGW)**: 온프레미스 네트워크 측의 VPN 장치.

#### AWS Direct Connect (다이렉트 커넥트)

**AWS Direct Connect**는 온프레미스 네트워크와 AWS 간에 **전용의 물리적인 네트워크 연결**을 제공하는 서비스이다. 인터넷을 거치지 않으므로 더욱 안정적이고 빠르며, 일관된 네트워크 성능을 제공한다.

- **정의**: 사용자의 데이터 센터와 AWS 네트워크 간에 사설 전용 회선을 구축하여 직접 연결한다.
- **활용**: 대규모 데이터 전송, 일관된 고성능 및 저지연 연결이 필요한 경우, 또는 인터넷을 통한 데이터 전송에 대한 보안/규제 우려가 있을 때 사용한다.
- **특징**: VPN보다 더 높은 대역폭과 낮은 지연 시간을 제공하며, 인터넷 요금이 아닌 데이터 전송 요금이 부과된다.

#### VPN과 Direct Connect 연결 이중화

서비스의 가용성을 높이기 위해 단일 연결에 의존하지 않고 여러 개의 연결을 구성하는 것이다.

- **이중화 목적**: 하나의 연결에 장애가 발생하더라도 다른 연결을 통해 트래픽이 계속 흐르도록 하여 서비스 중단을 방지한다.
- **방법**:
    - **VPN 이중화**: 여러 VPN 터널을 구성하거나, 여러 Customer Gateway 장치를 사용하여 중복성을 확보한다.
    - **Direct Connect 이중화**: 여러 Direct Connect 연결을 다른 라우터나 다른 Direct Connect 위치에서 구성한다.
    - **VPN과 Direct Connect 조합**: Direct Connect를 주 연결로 사용하고, VPN을 백업 연결로 구성하여 비용 효율적이면서도 높은 가용성을 확보할 수 있다.

#### VPC 피어링 (VPC Peering)

두 개의 AWS **VPC를 직접 연결**하여 마치 같은 네트워크에 있는 것처럼 통신할 수 있게 하는 서비스이다. 주로 동일한 AWS 계정 내에서 또는 다른 AWS 계정의 VPC 간에 사용한다.

- **정의**: 두 VPC 간에 네트워크 연결을 생성하여, 프라이빗 IP 주소를 사용하여 트래픽을 직접 라우팅할 수 있게 한다.
- **활용**: 서로 다른 팀이나 프로젝트가 별도의 VPC를 사용하면서도 서로 통신해야 할 때, 또는 분리된 VPC에 있는 애플리케이션과 데이터베이스 간에 안전하게 통신해야 할 때 사용한다.
- **특징**: 중앙 집중식 게이트웨이가 없으며, 트래픽은 AWS의 백본 네트워크를 통해 직접 라우팅되므로 고성능을 제공한다.

#### VPC 피어링 제약

VPC 피어링은 강력하지만 몇 가지 제약 사항이 있다.

- **전이적 라우팅 불가 (Non-transitive)**: VPC A가 VPC B와 피어링되고, VPC B가 VPC C와 피어링되어도, VPC A는 VPC C와 직접 통신할 수 없다. 각 VPC 쌍마다 개별적으로 피어링 연결을 설정해야 한다.
- **겹치는 CIDR 블록 불가**: 피어링하려는 두 VPC의 IP 주소 범위(CIDR 블록)가 겹쳐서는 안 된다.
- **단일 리전 (대부분)**: 일반적으로 동일 리전 내에서 피어링한다. 다른 리전 간 피어링도 가능하지만, 추가 비용이 발생하고 일부 제약이 있을 수 있다.

#### Transit Gateway (트랜짓 게이트웨이)

**Transit Gateway**는 **수많은 VPC와 온프레미스 네트워크를 중앙에서 연결하고 관리**할 수 있게 해주는 네트워크 허브 서비스이다. VPC 피어링의 전이적 라우팅 제약을 해결한다.

- **정의**: 수많은 VPC, 온프레미스 네트워크, 그리고 다른 AWS 계정의 네트워크를 연결하는 중앙 집중식 라우팅 허브이다.
- **활용**: 대규모의 분산된 네트워크 환경에서 복잡한 피어링 연결을 단순화하고, 네트워크 관리를 중앙 집중화하며, 확장성을 높일 때 사용한다.
- **특징**: 전이적 라우팅을 지원하여, Transit Gateway에 연결된 모든 VPC와 온프레미스 네트워크는 서로 통신할 수 있다. 이는 VPC 피어링의 `n*n` 연결 복잡성을 `n`개의 연결로 줄여준다.

## ❓ 궁금한 점

- **AWS Lambda는 서버리스 컴퓨팅의 대표적인 서비스인데, '서버리스' 아키텍처가 제공하는 주요 이점과 한계점을 가지고 있나?**
    - AWS Lambda는 '서버리스' 컴퓨팅을 통해 개발 및 운영 효율성을 높이지만, 특정 워크로드에는 적합하지 않을 수 있다.
    - **주요 이점**
        - **운영 오버헤드 감소**: AWS가 서버 프로비저닝, 패치, 백업 등 인프라 관리를 전적으로 담당하므로, 개발자는 코드 작성과 비즈니스 로직에만 집중할 수 있다.
        - **자동 확장**: 트래픽 증가에 따라 자동으로 컴퓨팅 자원이 확장(Scale-out)되고, 트래픽 감소 시 축소되어 안정적인 서비스 운영이 가능하다. 개발자가 직접 확장성을 고려할 필요가 없다.
        - **종량 과금**: 코드가 실행된 시간에 대해서만(밀리초 단위) 요금이 부과되므로, 유휴 시간 동안의 비용 발생이 없어 매우 경제적이다.
        - **빠른 배포 및 반복**: 인프라 설정 없이 코드만 배포하면 되므로 개발 주기가 짧아지고 빠르게 기능을 추가하거나 변경할 수 있다.
        - **이벤트 기반**: S3 업로드, API 요청, 데이터베이스 변경 등 특정 이벤트가 발생할 때만 코드가 실행되어 효율적이다.
    - **한계점 및 고려할 단점**
        - **콜드 스타트(Cold Start)**: 일정 시간 비활성화된 Lambda 함수가 다시 호출될 때, 실행 환경을 준비하는 데 시간이 걸려 초기 요청에 대한 **지연 시간**이 발생할 수 있다.
        - **최대 실행 시간 제한**: Lambda 함수는 기본적으로 최대 15분까지만 실행될 수 있다. 이보다 긴 시간이 필요한 작업에는 적합하지 않다.
        - **복잡한 디버깅 및 모니터링**: 서버 환경에 직접 접근하기 어려워 문제 발생 시 디버깅이 복잡할 수 있으며, 분산된 로그와 지표를 통합하여 모니터링하는 데 추가적인 노력이 필요하다.
        - **상태 비저장(Stateless)**: Lambda 함수는 상태를 유지하지 않는 'Stateless' 방식으로 설계되어, 세션 정보나 영구적인 데이터 저장이 필요한 경우 외부 서비스(예: DynamoDB, S3)와 연동해야 한다.
        - **벤더 종속성**: AWS Lambda에 특화된 코드를 작성하게 되므로, 다른 클라우드 환경으로 이전하기 어려울 수 있다.
    - **Lambda에 적합하지 않은 워크로드**
        - **장시간 실행되는 배치 작업**: 최대 실행 시간(15분)을 초과하는 작업은 Lambda로 구현하기 어렵다.
        - **지속적인 컴퓨팅 자원이 필요한 서비스**: 항상 활성화되어 대기해야 하는 실시간 스트리밍 서버나 웹소켓 서버 등은 Lambda의 이벤트 기반 모델과 맞지 않을 수 있다.
        - **특정 OS나 하드웨어에 대한 세밀한 제어가 필요한 경우**: Lambda는 OS나 기반 인프라에 대한 접근을 제한하므로, 이러한 제어가 필요한 워크로드에는 EC2 인스턴스가 더 적합할 수 있다.
        - **콜드 스타트 지연이 치명적인 경우**: 매우 낮은 지연 시간을 요구하는 특정 실시간 인터랙티브 애플리케이션에는 콜드 스타트가 문제가 될 수 있다. (프로비저닝된 동시성으로 일부 완화 가능)
