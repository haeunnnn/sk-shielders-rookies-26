## 🧠 주요 개념 정리

### 1. IAM (Identity and Access Management): 인증 및 권한 제어

**IAM**은 AWS 리소스에 대한 접근을 안전하게 관리하는 데 사용하는 서비스다. 누가 AWS 리소스를 사용할 수 있는지(인증), 그리고 무엇을 할 수 있는지(권한 부여)를 제어하는 역할을 한다.

#### Root User (루트 사용자)

AWS 계정을 처음 생성할 때 사용하는 이메일과 비밀번호를 가진 사용자를 말한다. AWS의 모든 서비스와 리소스에 대한 **무한한 권한**을 가진다. 보안을 위해 **평상시에는 사용하지 않는 것**이 원칙이다. 대신 IAM 사용자를 만들어서 일상적인 작업을 수행해야 한다.

#### IAM User (사용자)

AWS 계정 내에서 특정 개인(개발자, 관리자)이나 애플리케이션을 나타내는 자격 증명이다. IAM User는 다음과 같은 방식으로 AWS에 접근한다.

- **콘솔(Console)**: `username/password`를 사용하여 웹 기반 AWS 관리 콘솔에 로그인한다.
- **CLI(Command Line Interface) / SDK(Software Development Kit)**: `Access Key ID`와 `Secret Access Key`를 사용하여 프로그래밍 방식으로 AWS 서비스에 접근한다.

#### IAM Group (그룹)

IAM User들을 묶어서 관리하는 논리적인 집합이다. 그룹에 정책을 할당하면 그룹에 속한 모든 사용자에게 동일한 권한이 자동으로 부여된다. 예를 들어, '개발팀' 그룹에 EC2 생성 권한을 가진 정책을 연결하면, '개발팀'에 속한 모든 사용자가 EC2를 만들 수 있게 된다.

#### IAM Policy (정책)

권한을 정의하는 JSON 형식의 문서다. **Allow(허용)** 또는 **Deny(거부)** 효과와 함께, 어떤 **액션(Action)**을 어떤 **리소스(Resource)**에 대해 수행할 수 있는지 명시한다.
IAM 정책의 가장 중요한 원칙은 **최소 권한 부여 원칙**이다. 사용자나 역할에게 필요한 최소한의 권한만 부여하여 보안 위험을 줄여야 한다.

**IAM 정책 종류**
- **관리형 정책**: AWS 또는 고객이 생성하고 여러 주체(User, Group, Role)에 **반복적으로 부여**하여 사용할 수 있는 정책이다. AWS에서 미리 만들어 둔 정책을 `AWS 관리형 정책`이라 하고, 사용자가 직접 만들어 둔 것을 `고객 관리형 정책`이라 한다.
- **인라인 정책**: 특정 IAM User, Group, Role에 직접 포함되어 **1회성**으로 사용되는 정책이다. 이 정책이 속한 주체가 삭제되면 정책도 함께 삭제된다.

#### IAM Role (역할)

임시 자격 증명을 제공하는 특수한 IAM 주체다. `User`와 달리 직접 로그인하는 방식이 아니라, 특정 주체가 **임시로 역할을 가정(Assume)**하여 그 역할이 가진 권한을 행사한다.

- **User가 역할을 가정**: AWS 계정 내의 사용자나, 다른 AWS 계정의 사용자가 특정 역할을 가정하여 권한을 얻는다. `계정 내/계정 간` 접근 제어에 사용한다.
- **서비스가 서비스를 접근**: EC2 인스턴스가 S3에 파일을 업로드하거나, Lambda 함수가 DynamoDB에 데이터를 쓸 때, 해당 서비스에 IAM Role을 연결하여 안전하게 권한을 부여한다.
- **자격 증명 연동**: 회사 내의 인증 시스템을 AWS와 연동하여 사용자가 SSO(Single Sign-On) 방식으로 AWS 리소스에 접근하게 할 때 사용한다.

#### AWS 리소스 접근 제어 방식

AWS에서는 크게 두 가지 방식으로 접근을 제어한다.

- **사용자 중심 기반**: **IAM 정책**을 사용한다. User, Group, Role에 정책을 연결하여 '이 사용자/그룹/역할은 이 리소스에 접근할 수 있다'고 정의한다.
- **리소스 중심 기반**: S3, Glacier, KMS, SQS 등 일부 서비스는 자체적으로 **리소스 기반 정책**을 가진다. '이 리소스는 저 사용자/역할의 접근을 허용한다'고 정의한다.

### 2. 로드 밸런서 (Load Balancer)와 EC2 오토 스케일링

웹 서비스의 안정성과 성능을 높이는 데 필수적인 개념들이다.

#### 로드 밸런서 (Load Balancer)

네트워크 트래픽을 여러 서버(EC2 인스턴스)에 **분산**시키는 장치 또는 서비스다. 트래픽이 한 서버에만 집중되는 것을 막아 서버 과부하를 방지하고, 서비스의 안정성과 확장성을 확보한다.

#### 로드 밸런서의 기능 및 종류
- **부하 분산**: 들어오는 트래픽을 여러 서버에 효율적으로 분배한다.
- **상태 확인**: 등록된 서버들의 상태를 주기적으로 확인하여, 문제가 있는 서버로는 트래픽을 보내지 않는다.
- **세션 유지**: 특정 사용자의 요청이 항상 동일한 서버로 연결되도록 한다.

AWS는 세 가지 주요 로드 밸런서 종류를 제공한다.
- **Application Load Balancer (ALB)**: HTTP/HTTPS 트래픽을 분산하는 데 최적화되어 있다. URL 경로, 호스트 헤더 등 다양한 규칙을 기반으로 트래픽을 라우팅할 수 있다.
- **Network Load Balancer (NLB)**: 초고성능 및 저지연이 필요한 TCP/UDP 트래픽을 분산하는 데 적합하다.
- **Gateway Load Balancer (GLB)**: 네트워크 가상 어플라이언스를 관리하고 확장하는 데 사용한다.

#### 로드 밸런서 생성 및 작동 확인

AWS 콘솔에서 로드 밸런서를 생성하고, 여러 EC2 인스턴스를 '타겟 그룹'으로 등록한다. 이후 로드 밸런서의 DNS 주소로 접속하면, 로드 밸런서가 등록된 인스턴스들로 트래픽을 분산시키는 것을 확인할 수 있다.

#### EC2 오토 스케일링 (Auto Scaling)

EC2 인스턴스의 개수를 자동으로 조절하여 애플리케이션의 가용성과 성능을 유지하는 기능이다.

- **정의**: 트래픽 증가에 따라 자동으로 EC2 인스턴스를 늘리고(Scale-out), 트래픽 감소에 따라 인스턴스를 줄이는(Scale-in) 서비스다.
- **주요 기능**:
    - **자동 확장**: CPU 사용량과 같은 특정 지표(Metric)가 설정된 임계값을 초과하면 자동으로 인스턴스를 추가한다.
    - **자동 축소**: 지표가 낮아지면 불필요한 인스턴스를 자동으로 제거하여 비용을 절감한다.
    - **상태 확인**: 문제가 발생한 인스턴스를 감지하여 자동으로 교체한다.
- **활용**: 로드 밸런서와 함께 사용하여 예측 불가능한 트래픽 변동에도 안정적으로 서비스를 운영할 수 있다. 예를 들어, 트래픽이 급증하면 오토 스케일링이 인스턴스를 추가하고, 로드 밸런서가 새로운 인스턴스로 트래픽을 분산시키는 식으로 동작한다.

### 실습 주제 1: 버킷 정책을 활용한 S3 권한 제어
- 콘솔 > S3 > 버킷 생성
    - 버킷 이름은 유일하게
    - 버킷 생성 후 파일 업로드 및 다운로드
    - 퍼블릭 권한 주기 : 버킷 > 권한 >> 버킷 정책

### 실습 주제 2: S3를 이용한 정적 웹사이트 호스팅 및 버전 관리
- 콘솔 > S3 > 버킷 생성
    - 버킷 생성 후 파일 업로드 : `index.html`
    - 속성 > 정적 웹사이트 호스팅 활성화
    - 웹페이지 로드 X
    - S3 퍼블릭 권한 갖도록 하기 (버킷 정책) : 정책 생성기 활용
    - 웹페잊 로드 O
- 버전 관리 활성화
    - 속성 > 버전 관리 enable
    - 삭제 후 복원 확인 (객체 >> 버전 표시 : 삭제 마커 취소)

### 실습 주제 3: ELB & ASG의 활용을 통한 고가용성
- 기존 NW 환경 확인
- 보안 그룹 생성 : `sgalb`, `sgweb`
- 대상 그룹 생성 : 콘솔 > EC2 >> 대상 그룹 - `mytg`
- ELB 생성 : 콘솔 > EC2 >> ELB - `myalb`
    - ALB 선택 : 두 개의 퍼블릭 서브넷에 외부 ELB
- 런치 템플릿 생성 : 콘솔 > EC2 >> 런치 템플릿 - `XXlt`
    - AMI(이전 실습에서 만든 고객 생성 AMI), t3.micro, 보안 그룹
- Auto Scaling 그룹 생성 : 콘솔 > EC2 >> AutoScaling 그룹 - `myage`
- 대상 그룹 상태 확인
    - 상태 확인 : healthy

## ❓ 궁금한 점

- **루트 사용자(Root User)를 사용하지 않는 이유는 무엇이며, 어떻게 보호해야 할까?**
    - 루트 사용자는 AWS 계정의 모든 권한을 가진 사용자이기 때문에, 탈취당하면 계정 전체가 위험에 빠진다.
    - 주요 위험 요소 : 계정 내 모든 리소스 탈취 및 삭제. 예상치 못한 막대한 비용 발생. 모든 보안 설정 무력화.
    - 보호 방안
        - MFA(Multi-Factor Authentication)를 반드시 활성화한다.
        - 일상적인 작업에는 IAM 사용자를 사용하고, 루트 사용자는 사용하지 않는다.
        - 루트 사용자에게 할당된 액세스 키를 삭제하거나 비활성화한다.

- **ALB, NLB, GLB는 어떤 기준으로 선택해야 하나?**
    - 각 로드 밸런서는 처리하는 트래픽의 종류와 요구사항에 따라 명확히 구분된다.
        - **Application Load Balancer (ALB)**
            - HTTP/HTTPS 트래픽을 처리하며, URL 경로 등 콘텐츠 기반으로 트래픽을 분산할 때 사용한다. 웹 애플리케이션에 적합하다.
        - **Network Load Balancer (NLB)**
            - 초고성능과 저지연이 중요하고, TCP/UDP 트래픽을 분산해야 할 때 사용한다. 고정 IP가 필요한 경우에도 적합하다.
        - **Gateway Load Balancer (GLB)** 
            - 방화벽, IPS 등 네트워크 가상 어플라이언스의 트래픽을 관리하고 확장해야 할 때 사용한다.
