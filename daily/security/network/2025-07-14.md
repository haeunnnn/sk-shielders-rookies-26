## 🧠 주요 개념 정리

### 1. 패킷 필터링

#### 캡처 필터
- 패킷 수집 전에 조건을 걸어, 필요한 트래픽만 수집하도록 제한
- 와이어샤크에서 사용하는 필터링 문법 기반
    - 예시 : `tcp port 80` → TCP 80번 포트의 패킷만 캡처
- 패킷 수 자체를 줄여 성능과 저장 공간 최적화 가능
- 캡처 필터는 pcapng 파일에도 영향을 줌 (필터링된 것만 저장되기 때문)

**캡처 데이터 자동 저장 (자동 파일화)**
- 일정 조건(용량, 시간 등)에 따라 자동으로 새로운 pcapng 파일 생성
- 디스크 공간 관리와 장기 캡처에 유리

**자동 정지 조건**
- 파일 개수 또는 시간/용량 초과 시 자동 정지 가능

#### 디스플레이 필터
- 수집된 패킷 중에서 화면에 보여줄 데이터만 걸러줌
- 수집된 데이터는 그대로 보존되고, 화면 출력만 필터링
- 와이어샤크 전용 문법 사용
    - `(tcp.flags.syn == True) && (tcp.flags.ack == False)`

| 항목 | 캡처 필터 | 디스플레이 필터 |
| ---- | ------- | ------------- |
| 적용 시점 | 패킷 수집 전에 | 패킷 수집 후 |
| 필터 대상 | 수집 자체 제한 | 수집된 것 중 화면 표시 제한 |
| 문법 | BPF 문법 (libpcap) | 와이어샤크 전용 문법 |
| 성능 영향 | 수집량 자체를 줄여 성능 향상 | 성능에 영향 없음 (단지 필터링) |
| 예시 | `tcp port 443`   | `ip.src == 192.168.0.1` |

### 2. 분석 방식: 컴파일러 vs 인터프리터

#### 컴파일러 방식(번역)
- 전체 코드를 한 번에 분석하고 실행 가능한 형태로 변환
- 분석 시 지연이 있지만 실행은 빠름

#### 인터프리터 방식(통역)
- 한 줄씩 해석하며 실시간 실행
- 즉시 분석 가능하나 속도는 상대적으로 느림

#### 와이어샤크 분석 방식
- 인터프리터 기반 분석기
    - 한 줄 캡처 → 한 줄 분석
    - 실시간으로 패킷을 해석하고 보여주지만, 분석에 시간이 너무 오래 걸리기 때문에 패킷 수집은 **TCPdump**(Linux)나 **TShark**(Window)을 사용

### 3. MTU와 MSS 비교
| 항목 | 설명 |
| --- | ---- |
| **MTU (Maximum Transmission Unit)** | 네트워크 계층에서 한 번에 전송 가능한 최대 데이터 크기 (이더넷 기준 1500바이트) |
| **MSS (Maximum Segment Size)** | 전송 계층(TCP)에서 한 번에 전송 가능한 데이터(payload) 크기 (MTU - IP/TCP 헤더) |
| **계산 예시** | MTU: 1500 → IP 헤더 20 + TCP 헤더 20 = 40 → MSS = 1460바이트 |

- MTU 초과 시 **조각화(fragmentation)** 발생 가능 → 성능 저하 우려

``` text
┌──────────────┬───────────────┬────────────┬──────────────────────────────────┬─────────┐
│   Ethernet   |   IP Header   |    TCP     |             Payload              │   FCS   │
│    Header    |               |   Header   |                                  |         │
└──────────────┴───────────────┴────────────┴──────────────────────────────────┴─────────┘
    14 byte         20 byte       20 byte                1460 byte                4 byte
```

- 1518 Byte = LAN 카드가 내보내는 실제 데이터 = Ethernet Header + IP Header + TCP Header + TCP Data
- 1500 Byte = IP Header + IP Data
- 최적의 MSS = MTU - IP Header - TCP Header

### 4. L3 vs L4 단편화 비교

#### 3계층(IP 계층) 단편화
- IP 계층에서 패킷이 MTU보다 크면 조각화 수행
    - `MSS > Payload`인 경우, L4에서 단편화 X → L3에서 단편화
    - `MSS < Payload`인 경우, L4에서 단편화 O
- 조각화 시 다음 필드를 사용
    - `Identification`: 조각끼리 같은 패킷임을 나타냄
    - `Fragment Offset`: 데이터 위치
    - `MF (More Fragment) Flag`: 마지막 조각 여부
- 수신 측 재조립 시 복잡 → 순서 재조합, 유실/중복 체크 필요

#### 4계층(TCP 계층) 단편화
- 송신자가 TCP 전송 단위(MSS)를 고려해 미리 데이터를 나눔
- 조각화 대신 시퀀스 번호 기반으로 수신 측이 재조립
- 3계층보다 안정적이고 효율적 → 성능 및 지연 최소화
- 단, TCP에서만 가능 (UDP 등은 자체 분할 불가)

| 구분 | 3계층 단편화 | 4계층 단편화 (TCP) |
| --- | ----------- | ---------------- |
| 수행 위치 | 라우터 or IP 계층 | 송신지 TCP |
| 재조립 기준 | ID + Offset + Flag | 시퀀스 번호 |
| 적용 가능 계층 | 모든 IP 패킷 | TCP 전송에 한정 |
| 성능 영향 | 큼 (지연 및 리스크 존재) | 적음 (선제 분할) |
| 권장 여부 | X (가능한 한 회피) | O (성능적 장점) |

### 5. 오류 검출 방식
- **오류 검출** : 수신자가 데이터가 손상되지 않았는지 확인하는 과정
- **송신자** : 오류 검출 코드를 계산하여 헤더에 포함
- **수신자** : 수신 데이터로 같은 방식의 코드를 계산 → 두 코드 비교하여 무결성 점검

| 프로토콜 | 체크 대상 | 비고 |
| ------- | -------- | --- |
| **TCP/UDP** | TCP/UDP 헤더 + 데이터 (Pseudo Header 포함) | 전송 계층 |
| **IP (IPv4)** | IP 헤더만 | 데이터는 포함 안 됨  |
| **ICMP** | ICMP 헤더 + 데이터 | 오류 보고 등에서 필수 |

### 6. ICMP (Internet Control Message Protocol)

- **역할** : IP의 한계를 보완하기 위해 네트워크 상태 및 오류를 통신
- **작동 계층** : IP 계층에서 동작, IP와 함께 캡슐화됨
- **예시** : ping, traceroute → ICMP Echo Request/Reply 사용

#### UDP / IP의 보완 프로토콜

| 항목 | 특징 | 보완 프로토콜 |
| --- | ---- | ---------- |
| **UDP** | 비연결, 비신뢰 (재전송 없음) | TCP가 보완 (연결/신뢰 |
| **IP**  | 비신뢰, 비연결, 오류보고 불가 | ICMP가 보완 (오류 감지/보고) |

#### ICMP 헤더 구조

``` text
┌───────────────────┬───────────────────┬───────────────────────────────────────┐
│       Type        │       Code        |               Checksum                |
│      8 bit        │       8 bit       |                16 bit                 │
├───────────────────┴───────────────────┴───────────────────────────────────────┤
│                                 Rest of Header                                |
│                                                                               │               
├───────────────────────────────────────────────────────────────────────────────┤
│                                     Data                                      │
│                                                                               │               
└───────────────────────────────────────────────────────────────────────────────┘
```

| 필드 | 설명 |
| --- | ---- |
| Type | 메시지의 종류 (예: 8 = Echo Request) |
| Code | 세부 유형 (예: 목적지 도달 불가의 이유) |
| Checksum | 오류 검출용 필드 |
| Rest of Header | 각 메시지 종류별 세부 필드 포함 |

#### ICMP 도식화 예시 (ping 과정)

``` text
[Host A]  --- Echo Request (Type 8, Code 0) --->  [Host B]
[Host A]  <--- Echo Reply   (Type 0, Code 0) ---  [Host B]
```

### 7. Ethernet Frame 주소 체계
- **Ethernet II (DIX v2.0)** : PC/Host에서 사용하는 기본 프레임
- **IEEE 802.3** : 스위치 등 장비 간 통신에서 주로 사용

#### Ethernet Frame 헤더 필드

``` text
┌──────────────┬───────────────┬───────────────┬────────┬─────────────────────────┬─────────┐
│   Preamble   |  Destination  |     Source    |  Type  |          Data           │   FCS   │
│    Header    |    Address    |    Address    |        |                         |         │
└──────────────┴───────────────┴───────────────┴────────┴─────────────────────────┴─────────┘
     8 byte         6 byte           6 byte      2 byte         46 - 1500 byte       4 byte

┌──────────────┬───────────────┬───────────────┬──────────┬─────────────────────────┬─────────┐
│   Preamble   |  Destination  |     Source    |  Length  |          Data           │   FCS   │
│    Header    |    Address    |    Address    |          |                         |         │
└──────────────┴───────────────┴───────────────┴──────────┴─────────────────────────┴─────────┘
     8 byte         6 byte           6 byte       2 byte         46 - 1500 byte       4 byte

```

| 필드 | 설명 |
| --- | ---- |
| Destination MAC | 수신 측 MAC 주소 |
| Source MAC | 송신 측 MAC 주소 |
| EtherType / Length | 상위 계층 구분 (IPv4: 0x0800 등) |

### 8. ARP (Address Resolution Protocol)

**ARP 작동 목적**
- **IP 주소** → **MAC 주소** 변환 (IPv4 환경)
- 전송 전에 실제 MAC 주소를 알아야 프레임을 보낼 수 있음

#### ARP 헤더 필드

``` text
┌────────────────────────────────────────────┬────────────────────────────────────────────┐
│            Hardware Type                   │          Protocol Type                     │
│                                            │                                            │
├──────────────────────┬─────────────────────┼────────────────────────────────────────────┤
│        Hardware      |       Protocol      |                    Operation               │
│         length       |        length       |               request 1, reply 2           │               
├──────────────────────┴─────────────────────┴────────────────────────────────────────────┤
│                                Sender hardware address                                  │
│                                                                                         │               
├─────────────────────────────────────────────────────────────────────────────────────────┤
│                                Sender protocol address                                  │
│                                                                                         │
├─────────────────────────────────────────────────────────────────────────────────────────┤
│                                Target hardware address                                  │
│                                                                                         │
├─────────────────────────────────────────────────────────────────────────────────────────┤
│                                Target protocol address                                  │
│                                                                                         │
└─────────────────────────────────────────────────────────────────────────────────────────┘
                                                       \                           /
┌──────────────┬───────────────┬───────────────┬──────────────────────────────────┬─────────┐
│   Preamble   |  Destination  |     Source    |  Type  |          Data           │   CRC   │
│   and SFD    |    Address    |    Address    |        |                         |         │
└──────────────┴───────────────┴───────────────┴──────────────────────────────────┴─────────┘

```

| 필드 | 설명 |
| --- | ---- |
| Hardware Type | Ethernet(=1) |
| Protocol Type | IPv4(=0x0800) |
| Operation | 1=Request, 2=Reply |
| Sender MAC/IP, Target MAC/IP 포함 | |

#### ARP 동작 절차
1. **ARP Request** : 브로드캐스트 방식으로 송신
2. 수신자가 본인 IP와 일치 시 → **ARP Reply**로 응답 (Unicast)
3. 송신자는 응답의 MAC 주소를 **ARP Cache Table**에 등록
4. 이후 동일 목적지 통신 시에는 ARP 생략 가능

#### ARP Cache Table 갱신 과정
1. 수신된 Ethernet Frame의 **MAC 주소** 확인
2. **역캡슐화** → IP 헤더 분석
3. ARP Cache Table에서 해당 IP 주소 유무 확인
4. 없으면 새로 추가
5. 필요 시 ARP Reply 전송

#### ARP 취약점
- **스푸핑 공격** 가능 (ARP Reply를 위조해 MAC 주소를 속임)
- 보안 보완 필요 → 동적 ARP 검사 (DAI), 정적 MAC 설정 등

### 실습 주제 1: 와이어샤크 필터링 및 캡처 자동 저장해보기
- 다양한 와이어샤크 필터링 문법을 적용하여 패킷 필터링
- 캡처 옵션을 통해 특정 조건 달성 시 자동 파일화

### 실습 주제 2: CLI 환경에서 TShark로 패킷 수집하여 저장해보기
- `tshark -D` : 패킷을 캡처할 수 있는 네트워크 인터페이스 목록 출력
- `tshark -i 5` : 특정 네트워크 인터페이스에서 트래픽 캡처
- `tshark -i 5 -a files:3 -b duration:10 -w myshark.pcapng`
    - `-a files:3` : 3개 파일 수집 후 자동 정지
    - `-b duration:10` : 10초 후에 다음 파일을 생성
    - `-w myshark.pcapng` : 추적파일명

## ❓ 궁금한 점

- **ARP 관련 취약점을 활용한 공격 방법에는 어떤 것이 있는가?**
    - **ARP 스푸핑 (ARP Spoofing) / ARP 캐시 포이즈닝 (ARP Cache Poisoning)** : 공격자가 네트워크 내의 특정 호스트나 게이트웨이(라우터)의 MAC 주소를 위조하여 자신의 MAC 주소인 것처럼 속이는 공격. 이를 통해 공격자는 특정 장치로 가야 할 트래픽을 자신에게로 우회시키거나, 두 장치 간의 통신을 가로챌 수 있다.(MITM)
